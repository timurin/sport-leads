# ADR-004 — Производственная цепочка и момент формирования спецификации

**Статус:** принято как целевая архитектура; amend Spec↔ТК (`2026-07-26`); amend Spec = план+факт + Documents registry (`2026-07-26`); **amend ProductionOrder + ProductionBatch (`11.1.1.1` / ADR-018, `2026-07-30`)**; **amend FG warehouse stages (`11.2.2.1` / ADR-019, `2026-07-30`)**  
**Контекст:** план производства, утверждённый состав и фактическое исполнение имеют разные жизненные циклы, но для 1С нужен единый документ-отчёт по затратам партии.

## Решение

### Производственная цепочка

Использовать цепочку: заказ покупателя → позиции заказа → номенклатура → модель/артикул → размеры и характеристики → **техническая карта (технология / состав order-line)** → **производственный заказ (`ProductionOrder`) → производственная партия (`ProductionBatch`)** → исполнение цехов на ТК → **складской приход ГП (`ready_to_ship`) → отгрузка/списание (`shipped`)** → **спецификация партии как сводный отчёт (план + факт)** → 1С.

**«Технология»** в этой цепочке = заполненная техническая карта (состав, объёмы операций, snapshot маршрута Stage 8), а не отдельный Spec-документ *до* создания ТК. Spec **не** hard prerequisite generate ТК (ADR-016 amend Spec↔ТК).

**ProductionOrder / ProductionBatch** (ADR-018): планировочная группировка существующих ТК; shop fact SoT остаётся на ТК (`11.3`–`11.10`); партия — предпочтительный родитель Spec Stage 7.

**Склад / ГП** (ADR-019): после Упаковки стадии `ready_to_ship` / `shipped` проводят Приход / Списание в регистре; остаток не на `Nomenclature` и не на Batch.

### Спецификация — документ, не модуль

Спецификация — **документ-отчёт** (не модуль платформы и не проводка регистра). Роль: собрать данные по выпуску партии заказа №X для обмена с 1С (партия = 1 ед. или 100% выполнения заказа).

Форма Spec = набор **блоков**, получающих данные со связанных полей платформы. Поля **не** редактируются свободно; правка только при elevated rights.

Логические блоки:

| Блок | Источник |
|------|----------|
| Что продали | Номенклатура (PRODUCT) позиции / заказа |
| Связи | Заказ покупателя; техкарты, из которых сформулированы данные |
| Материалы (сколько потратили) | Номенклатура типа MATERIAL (план из ТК + факт расхода) |
| Операции | Производственные операции / этапы: сколько сделали / за какое время |
| Кто сделал | Ответственный за операцию (оператор или группа) |

**Spec = сводный отчёт: план + факт в одной форме.** План опирается на заполненную ТК (состав, объёмы, маршрут). Факт подтягивается из исполнения партии / stage results / списаний — без отдельного «второго» отчётного контура вместо Spec. Версионирование и момент утверждения уточняются в Stage `7.1.1` (черновик плана до факта vs финальный отчёт после выпуска — детали сущностей, не смена роли документа).

### Документы — реестр ссылок, не отдельный контур на тип

Раздел **Документы** (контур продаж) — **единый справочник-реестр ссылок** на документы, которые **живут у своих родителей**. Пример: счёт на оплату хранится в контуре продаж на заказе покупателя; фильтр «Счета на оплату» в Документах выдаёт строки всех таких счетов.

В реестре рядом могут отображаться ссылки на: счета, товарные накладные, техкарты, спецификации и др.

**Пока не** разрабатывать отдельный контур/модуль на каждый тип документа. Сущность Spec по-прежнему создаётся в Stage 7 у своего родителя (заказ / партия / ТК-контекст); реестр Документы — поздний cross-cut index, не prerequisite Stage 7/8/9.

## Последствия

- Order-line SoT состава — техническая карта; Spec читает ТК + факт, не заменяет ТК.
- Сравнение плана и факта доступно **внутри** формы Spec; сырые факты исполнения остаются в своих контурах (партия, stage results, складские движения).
- В 1С уходит Spec как сводный документ затрат партии (плюс при необходимости связанные движения).
- Навигация «Документы» не плодит CRUD-модули на тип; фильтр + deep-link в родителя.

## Ограничения

Спецификации, агрегированный факт партии (`11.2`), реестр Документы и интеграция с 1С пока не реализованы. Домен ProductionOrder/Batch зафиксирован ADR-018 (`11.1.1.1`); реализация DB/API/UI — `11.1.1.2`–`11.1.1.5`.
