# ADR-030 — Tech-card QR and shop scan

**Status:** принято (`2026-08-24`)  
**Date:** `2026-08-24`  
**Roadmap:** Stage `25` (`25.0.1`–`25.0.2` contract)  
**Amends:** ADR-016 (unit-line location + split WIP; one computed TC status); ADR-019 / `12.3.2` (FG post qty = arriving units, not whole card); ADR-029 (take/queue after split: units on Пошив, not «карта целиком»)  
**Depends on:** ADR-016, ADR-017, ADR-019, ADR-023, ADR-024 (`17.1.2.8` stage executors), ADR-029, print `18.3.8`  
**Evidence:** `docs/tasks/v1.00-stage-25-tech-card-qr.md` (`SL-TECH-CARD-QR-v1`)

## Контекст

Печатная техкарта (`18.3.8`) и цеховые модули (`11.4`–`11.10`) уже есть, но исполнитель не сканирует документ: маршрут двигается с ПК, карта целиком на одном шаге, приход ГП (`12.3.2`) постит `TC.quantity − scrap`. Нужен **один QR** на лист: скан с личного телефона или цехового планшета (свой `PlatformUser`, не общая учётка цеха) **и** двигает маршрут, **и** требует факт цеха. Часть штук может уйти вперёд или вернуться назад **без** дочерних ТК. Журнал пошива Stage 24 остаётся SoT резерва швей.

Нельзя: угадываемый QR = `id` карты; прыжки через цех; второй канбан-статус рядом с unit-line WIP; постинг всей карты, когда на `ready_to_ship` пришла только часть штук; child TC на цех.

## Решение

### 1. Один QR, непрозрачный токен (`25.1`)

| Есть | Нет |
|------|-----|
| Один токен на `TechnicalCard`, unique, cryptographically random / UUID | QR с открытым `technical_card.id` / номером / порядком |
| Печать токена (и URL скана) на форме `18.3.8` | Второй QR на единицу / цех / сторону листа |
| Резолв только по токену | Публичный скан без сессии |

Токен выдаётся при generate или при первой печати (реализация `25.1.1`). Перевыпуск — отдельное действие, не в MVP. Старый токен после перевыпуска не резолвится.

Хост скана (план `25.2`): путь с токеном, не с numeric id.

### 2. Актёр и цех

- Актёр = сессия `PlatformUser` (ADR-023). Телефон и планшет/ПК — **свой** логин.
- Разрешённые цеха скана = пересечение:
  1. **current или next** относительно локации **выбранных** unit lines (порядок маршрута этой ТК);
  2. привязки `17.1.2.8` (`platform_user_stage_access`) с тем же role_fallback, что shop (`shop_operator` / `admin` пока справочник пуст).
- Пошив дополнительно требует `sewing_cabinet.write` для команд журнала (ADR-029).
- Если пересечение даёт **несколько** цехов — UI спрашивает (picker, `25.2.2`). Ноль — отказ (403/422), не угадывать.
- **Skip запрещён:** нельзя выбрать цех дальше чем next и нельзя «перепрыгнуть» промежуточный шаг маршрута.

Restricted sewer (`read_own` без `read_any`): скан-хост в allowlist, если целевой цех = Пошив; остальной ERP по-прежнему режется (`24.1.2`).

Новые permission codes в этом контракте **не** вводятся.

### 3. Скан = маршрут + факт (option C)

Одна операция скана не может закрыть шаг «только факт» или «только сдвиг» в обход другого. Команды (`25.3.1`):

| Команда | Смысл |
|---------|--------|
| **Принята в работу** (`accept`) | Unit lines встают в работу на выбранном current цехе |
| **Готова и передана** (`complete_transfer`) | Требует shop fact этого цеха; выбранные unit lines переходят на **next** |
| **Возврат** (`return`) | Требует факт/причину цеха по правилам модуля; выбранные unit lines на **previous**; partial qty разрешён |

Partial qty = подмножество unit lines, не дробление одной строки на 0.5 штуки (unit line = 1 физическая единица, ADR-016 §2).

Факт цеха **не** дублируется новым документом:

| Цех | Факт |
|-----|------|
| Раскрой / Печать | Поля `11.5` / `11.6` (материалы `fact_qty`, duration, start/ready, WC на печати) + hard-gate `9.3.4` на complete/transfer |
| Дизайн / ВТО / ОТК / Упаковка | Существующие поверхности `11.4` / `11.8`–`11.10` |
| Пошив | Скан пишет **журнал Stage 24** (те же пулы, take/complete/release, снимок цены). `11.7` stage fact не заменяет журнал |
| `ready_to_ship` / `shipped` | Не цеховой fact; складской пост — §6 |

### 4. Остаток на unit lines (не child TC) — `25.0.2`

Одна ТК на order-line. WIP-разрез **по штукам**:

Логические поля unit line (колонки в `25.1`/`25.3`, не в этом срезе):

- `production_stage_id` — **текущая локация** штуки на маршруте этой ТК (FK `production_stages`);
- `last_transfer_kind`: `accept` \| `forward` \| `return` \| null — чтобы отличить отставание из-за возврата от ещё не переданных штук.

Плановый объём цеха для скана = число unit lines с этой локацией (минус брак ОТК, если штука списана scrap — такие строки не в live WIP).

**Нет** второй таблицы «остатков цеха». **Нет** дочерних ТК.

После Stage 25 очередь кабинета швеи = ТК, у которых **есть live unit lines на Пошив**, а не «текущий шаг карты = Пошив целиком» (amend ADR-029).

### 5. Один статус ТК (не второй канбан-SoT)

`TechnicalCard.status` (`draft` / `in_progress` / …) **не** размножается. Показ «статус техкарты» для списка/канбана/скана — **вычисляемый** read-model (`25.4.1`):

Порядок:

1. **Возврат** — если есть live unit line с `last_transfer_kind = return`, ещё не ушедшая вперёд снова → статус **возврат**.
2. Иначе по ship-readiness (локация `ready_to_ship` или `shipped` среди live, не scrap):
   - все live на `ready_to_ship`+ → **готова**;
   - часть → **частично готова**;
   - ни одной → **в работе**.

Канбан цеха по-прежнему группирует по `ProductionStage` / текущей локации штук; **не** заводит параллельную доску со своим enum.

### 6. Amend `12.3.2` / ADR-019 (частичный приход ГП)

Сегодня `compute_fg_receipt_qty` = `TC.quantity − Σ QC scrap` и один документ на карту.

После Stage 25:

- qty прихода при переходе выбранных unit lines на `ready_to_ship` = **число этих строк** (минус scrap именно этих штук, если применимо), **не** вся карта;
- уже оприходованные unit lines повторно не постятся (идемпотентность по штуке);
- несколько `fg_receipt` на одну ТК **разрешены**, пока не закрыт весь live объём;
- `shipped` / `fg_issue` — та же логика по штукам, которые реально отгружаются;
- rollback FG-стадии по-прежнему блокируется, если по затрагиваемым штукам уже есть непроведённый-отменённый документ (уточнение уникальности «один doc на карту» — в реализации `25.3`/`25.5`).

### 7. Границы

| Не в Stage 25 | Куда |
|---------------|------|

| Spec документ | Stage `7` |

| Общая учётка цеха | нет |
| Новые RBAC-коды скана | нет в контракте |

## Alternatives rejected

- QR = numeric id — перебор и утечка чужих карт.
- Скан только двигает маршрут **или** только факт — owner option C: оба.
- Child TC на цех / на пачку штук — ломает один документ и печатный лист.
- Общий пул qty на header без unit-line location — нельзя частичный возврат/передачу.
- Хранить «статус ТК» отдельным kanban SoT — расходится с локациями штук.
- Постить `TC.quantity` при первом `ready_to_ship` — оприходует штуки, которые ещё в цехах.
