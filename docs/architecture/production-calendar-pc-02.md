# PC-02 — архитектура Production Calendar v0.1

**Статус:** проектный контракт для согласования, 2026-10-03. **Реализации нет.** Основание: [PC-01](../tasks/production-calendar-pc-01-audit.md), `docs/roadmap/production-calendar-v0.1.md`, `roadmap-v1.1.md`, ADR-004/016/017/018/029/030/031/034. Этот документ описывает будущие **добавляющие** таблицы/API календаря; действующие модели, миграции и бизнес-правила не меняются.

**Ревизия 2026-10-05:** для реализации v0.1 действует [минимальный implementation contract](production-calendar-implementation-v0.1.md). Расширенные таблицы, независимые календарные статусы исполнения и API ниже — историческое предложение PC-02, не объём PC-03. UI-A–UI-H OWNER-APPROVED, DESIGN-APPROVED = true; PC-02.1 закрыт документационно. P1 B1 и проверки реализации сохраняются.

## 1. Граница и источник истины

Календарь — ручной план и диспетчерский журнал для **одной существующей standalone `TechnicalCard` контура B**. Отсутствие `SalesOrder` штатно. `TechnicalCardOrderGroup` остаётся владельцем ручного `order_number` (глобальная уникальность уже задана БД), ТК — количества, модели, варианта сборки, маршрута и факта цехов. `ProductionOrder`/`ProductionBatch` по ADR-018 остаются отдельными документами производства; календарь их не создаёт и не переименовывает. Новый `CalendarPlan` хранит только календарные снимки и ссылки, а не третий производственный заказ. На экранах «заказ календаря» означает этот план вместе с номером группы и выбранной ТК. Если в группе несколько ТК, каждая получает отдельный план; ключ отображения `{order_number} · {technical_card.number}` однозначен.

Создание плана: выбрать существующую standalone ТК; если пользователь начал с полей заказа без ТК, UI может направить в существующее создание standalone ТК, затем создать план отдельным действием. Календарный API не создаёт/меняет ТК. Сервис проверяет `card.order_group_id != null`, `sales_order_id == null`, совпадение ручного номера с группой, `quantity > 0`, модель/вариант/маршрут из ТК и наличие **снимка этапов ТК**. Поля формы `product_name`, `model`, `quantity`, `route` — подтверждение и показ **снимка ТК**, а не независимые изменяемые значения. Произвольное несовпадающее значение возвращает `422 field_conflict`. Неактивный или позднее изменённый master-маршрут сам по себе не портит уже утверждённый снимок ТК; сервис показывает `source_drift` и не копирует live-этапы поверх него. Ручной номер меняется только по действующим правилам группы, не через календарь. Срок календаря nullable и независим от обязательного `TechnicalCardOrderGroup.desired_date`; при создании предлагается срок группы, но пустой срок календаря разрешён. Это не меняет группу. Источник имени изделия — `TechnicalCard.nomenclature_name`; свободный текст допускается только как `display_name_snapshot` календаря, без изменения ТК.

`CalendarPlan` привязан к `technical_card_id UNIQUE`, `order_group_id` хранит FK для проверки принадлежности и поиска, `production_order_id` и `batch_id` в v0.1 отсутствуют. Если ТК привязали к SalesOrder позже, календарный план остаётся историческим, но новые операции/переходы блокируются до явного решения о переносе контура; автоматической конвертации нет. Удаление/отмена ТК после появления плана не каскадно удаляет план: FK `RESTRICT`, календарь показывает конфликт источника. Чтение master после создания служит только для предупреждений; снимки не меняются автоматически.

## 2. Семантика нормы пошива

Подтверждённое поле — `AssemblyOperationLine.duration_seconds` (целые секунды ≥0) и `quantity_per_item` (целое ≥1) внутри выбранного `AssemblyVariant` модели. Отдельного `ProductModel.sewing_time_per_unit_minutes` нет. **Решение владельца PC-02.1:** длительность применимой строки — норматив времени операции **на одно изделие для одной швеи**; `quantity_per_item` — число повторов операции на изделие, не число швей. Это решение относится к будущему календарному расчёту и не меняет действующие модели или правила ТК. Границы применимости и исключения: [проверка PC-02.1](../tasks/production-calendar-pc-02-1-validation.md).

Для выбранного варианта `unit_labor_seconds = Σ_applicable_lines(duration_seconds × quantity_per_item)`; `required_person_minutes = quantity × unit_labor_seconds / 60`. Применимость означает операции пошива на одно изделие; если вариант смешивает их с разовой подготовкой, работой иного участка или комплектом и нельзя надёжно выделить строки, автоматическая норма отсутствует. Нельзя фильтровать по названию или необязательному `sewing_operation_id`. В хранении — точные `Decimal` нормо-секунды, для ответа API — `Decimal` человеко-минуты/часы с согласованным округлением **только при отображении**. Суммируются трудозатраты разных моделей в человеко-минутах, не штуки и не машино-часы; трудоёмкость не равна длительности партии. `duration_seconds` на `TechnicalCardStageResult` — факт, а `ProductModelOperationNorm.norm_qty_per_item` — план объёма операции/материала; оба не являются заменой нормативу пошива. Вариант должен принадлежать модели ТК; если вариант отсутствует, строки пусты, есть применимая строка `duration_seconds=0` или некорректная единица — состояние `norm_missing`/`norm_unverified`, никакого 0% и автоматической оценки. Возможность и порядок утверждения ручной оценки для пошива остаются открытыми; если она разрешена, источник `manual` помечается автором и причиной и не записывается в вариант модели.

При создании плана снимок `CalendarLaborNormSnapshot` фиксирует `assembly_variant_id`, идентификаторы/длительности/кратность/применимость строк, `unit_labor_seconds`, `source_updated_at`, `unit=person_second_per_item`, `source_kind=assembly_variant|manual|missing`, основание решения о применимости и автора. Снимок иммутабелен; новое вычисление будущей незавершённой операции — явная ревизия с событием, предыдущий план/факт сохраняются. Изменение справочника не пересчитывает существующий план. В v0.1 вариант ТК — единственный автоматический источник нормы пошива; для иных цехов оценка — `person_minutes` на операцию или на единицу с явным scope и источником, без подстановки пошивной нормы. Для дизайна действует отдельная предварительная методика ниже.

### 2.1. Нагрузка отдела дизайна — решение владельца `2026-10-03`

Источник решения: [«Нагрузка отдела дизайна»](../tasks/pc-design-department-load-v0.1.md). Трудоёмкость **не равна тиражу × минутам на изделие**. Она складывается из создания/адаптации каждого самостоятельного дизайна, ручной подгонки каждого уникального размерного комплекта и каждой требующей работы детали, финальной проверки/экспорта/передачи файлов и отдельно обоснованных нестандартных работ. Один размер не принимается за один файл: состав файлов и деталей устанавливается по фактической модели и способу экспорта. Повторные экземпляры уже подготовленного размера сами по себе не создают повторную задачу дизайнера. Все слагаемые — человеко-минуты, итог `T_design / 60` — человеко-часы. Нормативы по видам работ пока **гипотезы для калибровки**, не утверждённые числовые стандарты MOSMADE.

Плановые входы: самостоятельные дизайны/варианты, тип работы (`new`, `adapt`, `reuse_without_changes`), применимые размеры и детали модели/лекал, способ подготовки (`manual` сейчас; автоматизация — отдельная будущая версия), объём проверки/экспорта и нестандартные работы. Существующие `TechnicalCardUnitLine` могут помочь получить размеры заказа, но число уникальных подготовок нельзя вывести только из числа строк или тиража. `DesignProject`/`DesignVersion` по ADR-021 привязаны к `SalesOrder` и не являются обязательным источником для standalone ТК. Календарь читает доступные данные, сохраняет **свой** снимок входов, версии предварительных нормативов, состав расчёта, источник оценки (`calculated|manual|missing`) и автора/причину ручной корректировки; конкретная добавляющая структура снимка и DTO требует отдельной задачи перед реализацией. Действующие ТК, лекала, модели и дизайн-активы не меняются. Если детализация недостоверна, показывается `norm_missing` либо **явно ручная предварительная оценка**, а не ноль или выдуманная точность.

Человеко-минуты дизайна распределяются по датам вручную; плановая сумма по датам не должна превышать утверждённую оценку без явной ревизии. Доступная мощность — человеко-минуты дизайнеров по сменам и эффективности из §3, процент рассчитывается общим правилом §3. Ожидание согласования заказчиком — календарная задержка/статус **без** занятости дизайнера. Условия согласования перед печатью, если они нужны для конкретного заказа, должны проверяться отдельно от трудоёмкости и календарного статуса дизайна; для standalone ТК нельзя молча требовать `SalesOrder.design_approval_status`. Конкретный gate согласования и его источник остаются предметом отдельного решения. План и факт остаются раздельными; будущая калибровка использует фактическое время цеха «Дизайн», не переписывая прошлые снимки. CorelDRAW-макрос и его отдельные нормы вне v0.1.

## 3. Мощности и расчёт дня

**Дополнение после решения владельца `2026-10-03`:** [нормативно-ресурсный контракт v0.1](production-calendar-capacity-v0.1.md) уточняет дизайн, четыре плоттера, каландр, общий ручной пул/лазер раскроя и бригаду упаковки. Для этих работ общий человеко-часовой агрегат ниже применим только к **персоналу**; машинные очереди и штуки/погонные метры требуют собственных единиц и проверки. Предлагаемая схема §5 и API §6 нуждаются в добавляющей ревизии до реализации, без изменения существующих моделей/ТК/маршрутов.

Единица мощности персонала — человеко-минуты. `CalendarCapacityRule` с FK на существующий `ProductionStage` задаёт эффективный диапазон дат, рабочие дни недели, число смен, минуты оплачиваемой производственной работы в смене **после перерывов**, число доступных работников **на каждую смену** и `efficiency` как `Decimal` в диапазоне `(0,1]` (значение настраивает администратор; 85% не зашито). Для разных смен — дочерние `CalendarShiftRule` с локальными началом/концом, `staff_count`, `productive_minutes`, `efficiency`; агрегат «число смен» вычисляется из них, а не умножает общую численность повторно. Пересекающиеся интервалы смен для одного и того же работника/ресурсной группы запрещены; v0.1 хранит агрегированное число работников, без именного расписания. `CalendarCapacityException` на `(stage_id, local_date, shift_key)` перекрывает базовую смену: выходной, укорочение, дополнительная смена, число вышедших работников, часы или эффективность; полная замена параметров на дату, не неоднозначная сумма поправок. Не заданная мощность = `capacity_unknown`; явно выходной/0 работников = `zero_capacity`.

Календарная дата трактуется в согласованной производственной timezone (предлагается `Europe/Moscow` как конфигурация, а не системная TZ сервера), timestamps в БД — aware UTC. Для дня `available_person_minutes = Σ(staff_count_shift × productive_minutes_shift × efficiency_shift)`; `planned_person_minutes` — сумма аллокаций этого цеха за день. При `available > 0` и полной известной норме `load_percent = planned / available × 100`, перегрузка строго `>100%`. При неизвестной норме хотя бы одной учитываемой аллокации загрузка не маскируется частичным процентом: ответ содержит `known_planned`, `unknown_task_count`, `load_state=norm_missing`; при неизвестной мощности — `capacity_unknown`; при нулевой мощности и плане — `over_capacity_without_shift`, без деления на ноль. 0% допустимо только при известной положительной мощности и нулевом плане. Для одного варианта справочно `floor(available_seconds / unit_labor_seconds)`, но это не второй лимит.

У закупки мощность в часах отсутствует: её готовность отслеживается статусом/сроком, не процентом. Для остальных цехов мощность в человеко-минутах применима только при заданном правиле и подтверждённой трудоёмкости: для дизайна — расчёт по §2.1 или явно ручная оценка, для других ненормированных цехов — ручная оценка. `WorkCenter` показывает назначенное оборудование ТК; человеко-часы из него не выводятся. Предупреждение о перегрузке не блокирует сохранение плана, но требует подтверждения и причины; 0/unknown capacity также требует явного подтверждения, а не ложного «свободно».

Проверочный пример проектной арифметики: две применимые строки варианта по `600 s × 1` дают `1200 s = 20 person-min` на изделие; `100` изделий требуют `2000 person-min = 33⅓ person-h`. При одной смене 8 рабочих часов и эффективности `0.8` мощность 8 швей = `3072 person-min`, 6 швей = `2304 person-min`; загрузка соответственно около `65.10%` и `86.81%`. Семантика времени на изделие/швею утверждена владельцем; значения смены/эффективности здесь только пример, не утверждённые настройки. Работа 14 человеко-часов, разнесённая как 8+6 по двум датам, учитывается один раз на каждой дате.

## 4. Граф зависимостей и исполнение календаря

`CalendarOperation` — плановая операция со снимком `TechnicalCardStageResult` (исходный `ShopRoutingStageLine` — лишь происхождение) и типом `route_stage` либо виртуальным `procurement_readiness`. `CalendarDependency` хранит рёбра DAG внутри одного плана. Две корневые ветви: закупка материалов и дизайн. Для поддерживаемого **снимка ТК** дизайн соответствует его реальному stage `design`; закупка — виртуальная операция без нового `ProductionStage` и без автоматической связи с `PurchaseOrder` (ADR-034). Печать начинается после **обоих** завершений. Дальше используются реальные шаги снимка ТК по `stage_order`: печать → раскрой → пошив → упаковка; дополнительные реальные ВТО/ОТК сохраняются в фактическом порядке. `ready_to_ship`/`shipped` остаются этапами ТК/склада, не трудовыми задачами календаря. Если снимок ТК не содержит требуемых узлов, имеет иной порядок или повторяет их неоднозначно, создание плана возвращает `422 unsupported_route` с деталями; граф не «исправляет» ни ТК, ни master-маршрут. Правило пропуска виртуальной закупки требует причины/автора и явного состояния `waived`; пропуск реального этапа ТК календарь не инициирует.

Планировать дочернюю операцию до завершения родителей разрешено. `start` на сервере требует все обязательные зависимости в terminal `completed` или разрешённом `waived` **и** отсутствие конфликта источника; иначе `409 dependency_blocked` со списком блокирующих узлов. Внутренний статус календаря: `unplanned`, `planned`, `in_progress`, `paused`, `completed`, `cancelled`, а `waived` допустим только для виртуальной закупки; `ready_to_start` вычисляется, не хранится. Разрешённые переходы: `unplanned|planned → in_progress` (после gate), `in_progress → paused|completed`, `paused → in_progress|cancelled`; `completed` и `waived` терминальны, отмена требует причины. Начало/завершение календарной операции пишет только календарный журнал. Оно **не вызывает** существующие `TechnicalCardStageResult.start/complete`, не меняет склад/закупки и не двигает цеховой канбан. UI обязан явно различать календарный диспетчерский статус и производственный факт ТК. До принятия отдельного интеграционного контракта автосинхронизации нет; расхождение показывается как предупреждение. Завершение реального этапа на ТК по прежним правилам не считается автоматическим завершением календарной операции.

## 6. Будущие API-контракты (без реализации)

Префикс `/production-calendar`; DTO отделены от ORM. Чтение требует `calendar.view`, планирование — `calendar.plan`, переходы — `calendar.execute`, мощности — `calendar.capacity.manage`; эти права предполагаются новыми и не расширяют существующие `shop.kanban.transition`/`technical_cards.create`. Создание и изменение используют `Idempotency-Key` для POST и `If-Match: version` для конкурентных PATCH/PUT; 409 — версия/зависимость/состояние, 422 — неверная связь/маршрут/параметр, 403 — доступ. Все даты — ISO `YYYY-MM-DD`, timestamps — ISO 8601 с offset, время труда — Decimal в минутах, проценты — Decimal. Ни один endpoint не принимает поле `sales_order_id`.

| Метод | Назначение / контракт ответа |
|---|---|
| `GET /references?technical_card_id=...` | Батч допустимых ТК, модели/варианта/маршрута и проверенных снимков; источники — действующие сервисы чтения, без создания альтернативных каталогов. |
| `POST /plans` | `{technical_card_id, order_number_confirmation, product_name?, due_date?, notes?, route_confirmation_id}`; транзакционно проверяет ТК/группу/снимок этапов, делает снимок и DAG; возвращает `plan_id`, `version`, `norm_state`, операции/предупреждения. Повтор по Idempotency-Key возвращает тот же результат. |
| `GET /plans?from=&to=&status=&limit=&cursor=` / `GET /plans/{id}` | Slim list и полный detail; отдельные поля `calendar_status` и `technical_card_status`, снимки и source-drift warnings. |
| `PATCH /plans/{id}` | Только календарные `due_date`, `display_name_snapshot`, `notes` в разрешённых состояниях; изменение qty/model/route требует явной новой ревизии плана, не тихого PATCH. |
| `PUT /operations/{id}/allocations` | Полная замена распределения операции с ожидаемой `version`, датами, временем/qty, причиной; возвращает пересчитанную нагрузку и `warnings`; overload требует `acknowledge_overload=true` и причину. Отмена/перенос — новая запись журнала. |
| `POST /operations/{id}/start|pause|complete|cancel` | Серверные gates DAG, статус/actor/reason, optimistic version; без мутации ТК. `GET /plans/{id}/events` — история. |
| `GET /board?week_start=&stage_ids=` / `GET /days/{date}?stage_id=` | Батч агрегатов по участкам/дням: available, known planned, unknown count, load state, percent nullable, task count, факт отдельно. Ссылки на задания; без row-by-row fetch. |
| `GET /timeline?from=&to=` / `GET /risks?from=&to=&kind=` | Плановые диапазоны и фактические отметки отдельно; риски из сохранённых дат/мощностей/DAG, без вымышленного прогноза. |
| `GET/PUT /capacity/rules`, `GET/PUT /capacity/exceptions` | Действующие правила и дневные исключения; `GET /capacity/days?from=&to=&stage_ids=` возвращает эффективную мощность и происхождение параметров. |

Протокол не подменяет существующие `GET /technical-cards`, `/product-models`, `/shop-routings`, `/production-stages`, `/work-centers`, `/purchase-orders`; сервис календаря читает их репозитории и делает снимки. Риск перегрузки вычисляется в одной транзакции с сохранением аллокаций; для затронутых `(stage,date)` нужен транзакционный advisory lock или отдельная блокируемая строка дня, чтобы параллельные правки не подтвердили одну мощность дважды.

## 8. Решения и вопросы

**Приняты как архитектурное предложение PC-02:** календарь = overlay над standalone ТК, номер принадлежит `TechnicalCardOrderGroup`; факт ТК и цехов не дублируется; DAG и плановые даты самостоятельны; закупка — виртуальная readiness-операция; мощности в человеко-минутах; нормы пошива читаются из варианта сборки и сохраняются снимком; перегрузка предупреждает, старт блокируется сервером; API только новые и добавляющие.

**Подтверждено владельцем в PC-02.1:** `duration_seconds` применимой операции — секунды работы одной швеи на одно изделие; сумма с `quantity_per_item` формирует трудоёмкость единицы. Неоднозначная применимость строк остаётся исключением без автоматического расчёта.

**Требуют подтверждения владельца до PC-03/реализации:**

1. Разрешён ли ручной норматив пошива при пустых/нулевых строках, кто его утверждает и достаточна ли причина? Без ответа загрузка остаётся `norm_missing`.
2. Допускается ли календарный план только для standalone ТК и отдельный план на каждую ТК группы; должен ли быть календарный план для контура A позже?
3. Является ли диспетчерское «Завершено» отдельным подтверждением или должно читать факт ТК? Пока контракт сохраняет их отдельно, чтобы не менять бизнес-логику.
4. Какие реальные маршруты поддерживать в v0.1 при отсутствии `design/print/cutting/sewing/packaging` или другом порядке; нужно ли включать ВТО/ОТК в загрузку и зависимости?
5. Что означает «закупка завершена» без складской обеспеченности: ручной флаг с документом-основанием или подтверждение поступления? Автоматическую проверку остатков/PO этот контракт не предполагает. Дефект [PC-02.1-B1](../tasks/production-calendar-pc-02-1-b1-refresh-model-material-loss.md) исключает вывод готовности из состава ТК.
6. Утвердить timezone предприятия, длительность рабочих смен после перерывов, лимит/тип численности по сменам и права календаря. Значения по умолчанию для численности/эффективности не придуманы.
7. Приоритет ручного срока календаря относительно обязательной даты standalone-группы; сейчас это независимый nullable срок, а различие показывается пользователю.

До ответов запрещено реализовывать спорные формулы, маршрутные переходы и запись факта. PC-03 не начат.
