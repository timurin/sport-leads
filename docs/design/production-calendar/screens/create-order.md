# PC-UI-05 — UI-B: быстрое добавление заказа

**Статус:** UI-A–UI-H = OWNER-APPROVED; DESIGN-APPROVED = true, `2026-10-05`, по [решению владельца](../../../tasks/pc-02-1-lightweight-design-freeze-implementation-contract.md). Дизайн зафиксирован; реализация не начата. Проверки runtime/Edge, ранее не выполненные, остаются техническими проверками реализации.

## Граница данных

Форма создаёт в будущем только календарный план **одной существующей standalone ТК**. Ручной номер заказа принадлежит `TechnicalCardOrderGroup`; поле номера служит поиску и подтверждению группы, не создаёт новую независимую нумерацию. Номер ТК выбирается из существующих ТК группы. Изделие — обязательная свободная подпись календарного снимка, исходное `TechnicalCard.nomenclature_name` не меняется. Модель, вариант сборки, количество и маршрут подтверждают снимок выбранной ТК; несовпадение не проходит проверку. Отсутствующий маршрут блокирует демонстрационное создание до настройки ТК. Плановая дата готовности необязательна, как в PC-02; прошедшая дата даёт явное предупреждение, но не подменяет срок группы ТК.

Норматив пошива: сумма применимых `duration_seconds × quantity_per_item` выбранного варианта — человеко-секунды на изделие для одной швеи; умножение на количество даёт трудоёмкость заказа. Нулевые/пустые применимые строки дают «Норма отсутствует» и «Нагрузка не рассчитана»; создание при этом разрешено, автоматического нуля нет. Прототип показывает сохранённый демонстрационный снимок и не перечитывает/правит модель. Если применимость строк неоднозначна, автоматическую числовую норму будущий сервис не утверждает (PC-02.1).

Схема «Закупка ∥ Дизайн → Печать → Раскрой → Пошив → Упаковка» относится только к календарным зависимостям. Линейный маршрут ТК не изменяется. После успешной локальной проверки показано «Заказ создан в календаре и ожидает распределения по датам»; фактического создания и распределения нет, UI-E проектируется отдельно.

## Компоненты и состояния

| Компонент | Состояния |
|---|---|
| Диалог | Desktop ≥1024px: до 1120px шириной, трёхколоночная форма, снимок и зависимости рядом; обычная и заполненная формы целиком видны на 1440×900 и 1366×768 без внутренней прокрутки. Tablet 768–1023px: две колонки и один скролл тела при нехватке высоты. Mobile ≤767px: fullscreen, один скролл тела, шапка и кнопки видны. Нативный `<dialog>`, `Escape`, закрытие, возврат фокуса на кнопку вызова. |
| Поля | Пусто, заполнено снимком, обязательное поле пусто, неверное количество, конфликт с выбранной ТК. Ошибка показана у поля и общим текстом; фокус переходит к первой ошибке. |
| Выбор источника | Поиск номера группы и номера ТК; три явно помеченных демо-сценария: с нормой, без нормы, без маршрута. |
| Снимок нормы | Модель и вариант, норматив на изделие, трудоёмкость заказа; при отсутствии нормы числовая нагрузка не выводится. |
| Срок | Дата в прошлом — предупреждение, не скрытая блокировка. |
| Завершение | Отмена закрывает диалог; создание показывает локальное подтверждение, не отправляет API-запрос и не планирует операции. |

## Сценарии просмотра

1. Открыть UI-A и нажать «Добавить заказ»: открывается UI-B с модальным окном. Закрыть по `Escape`, затем снова открыть кнопкой; фокус возвращается на кнопку в UI-B.
2. Нажать «Создать заказ» на пустой форме: видны ошибки номера, ТК, изделия, модели, варианта, количества и маршрута; фокус на первом поле.
3. Выбрать «С нормой»: `КД-041` / `КД-041-1`, 100 изделий, 360 с ×1 + 240 с ×2 = 840 с = 14 мин на изделие, трудоёмкость 23 ч 20 мин. Изменить количество на `0`, дробное и число, отличающееся от ТК: создание заблокировано.
4. Выбрать «Без нормы»: `КД-052`, нулевая строка показывает «Норма отсутствует», «Нагрузка не рассчитана»; демонстрационное создание разрешено.
5. Выбрать «Без маршрута»: `КД-061`; создание заблокировано с объяснением. Выбрать чужую модель/маршрут: конфликт с ТК также блокирует создание.
6. Ввести прошедшую дату: предупреждение видно до отправки; корректная форма допускает локальное подтверждение. Сообщение после создания не обещает назначенных дат.
7. Проверить 1440×900, 1366×768, 1280×800, 1024×768, 768×1024, 390×844 и 320×568: на desktop обычная форма целиком видна без скролла; на tablet/mobile доступен один скролл содержимого с закреплёнными шапкой и кнопками. Горизонтальной прокрутки нет.

## Предел прототипа

Локальные карточки, модели и маршруты служат только демонстрационными снимками. UI-B не реализует создание standalone ТК или новой группы; если нужной ТК нет, пользователь должен пройти действующий платформенный сценарий вне календаря. Минимальный реальный поток зафиксирован 2026-10-05 в implementation contract: выбор существующей ТК подставляет номер/модель/изделие/количество/маршрут; повторный ручной ввод не требуется. PC-02.1 закрыт документационно. Платформенные DS-SHELL-01/02 не редактировались.

## Уточнение PC-UI-05.1 · 2026-10-03

Диалог расширен до `min(1120px, 100vw − 48px)`; поля уплотнены в три смысловые строки по три колонки при ≥1024px, снимок нормы и схема зависимостей стоят рядом. При 768–1023px используются две колонки и один скролл тела; на mobile — одна колонка, fullscreen и один скролл тела с закреплёнными шапкой и кнопками. Порядок DOM/Tab не менялся. Нормальная и заполненная формы на desktop не прокручиваются. При одновременных ошибках, просроченном сроке и очень длинных строках добавляется класс `needs-scroll`: единственный скролл тела сохраняет доступ к сообщениям и нижним кнопкам. В 1024×768 такое сочетание физически превышает доступную высоту без уменьшения читаемого текста.

Edge/Chromium проверил 1440×900, 1366×768, 1280×800, 1024×768, 768×1024, 390×844, 320×568 и эквивалент масштаба 125% (CSS viewport 1152×720). Во всех случаях горизонтальная прокрутка отсутствует. На desktop/laptop `dialogScroll=0`, `bodyScroll=0`, все блоки и footer видны; на tablet/mobile `dialogScroll=0`, прокручивается только тело. Сочетание ошибок, предупреждения о прошедшей дате и строк 200/300 символов на 1366×768 и 1024×768 включает один скролл тела; footer остаётся в пределах экрана, длинный текст переносится. Нативный `Escape`, Tab/Shift+Tab, возврат фокуса, демо-норма и успешное создание проверены в Edge. Физическую экранную клавиатуру телефона headless Edge не эмулирует.
