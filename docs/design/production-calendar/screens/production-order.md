# PC-UI-06 — UI-C: карточка производственного заказа

**Статус:** UI-A–UI-H = OWNER-APPROVED; DESIGN-APPROVED = true, `2026-10-05`, по [решению владельца](../../../tasks/pc-02-1-lightweight-design-freeze-implementation-contract.md). Дизайн зафиксирован; реализация не начата. Проверки runtime/Edge, ранее не выполненные, остаются техническими проверками реализации.

## Граница экрана

Карточка показывает календарный план **одной существующей standalone ТК** в группе с ручным номером. Это не CRM `SalesOrder` и не новая бизнес-сущность `ProductionOrder`. Номер группы, ТК, модель, вариант, количество и маршрут — read-only снимок источника; подпись изделия находится в календаре. Плановая дата готовности, даты операций, календарные статусы и календарный факт принадлежат только календарю. Факт и маршрут ТК не изменяются. При несовпадении источника будущий сервис должен показать конфликт, а не править ТК из UI-C.

## Компоновка и переходы

Хлебные крошки и «К календарю» ведут в [UI-A](../weekly-board-prototype.html). После локального создания в [UI-B](../create-order-prototype.html) будущий переход должен открывать конкретный созданный план; прототип UI-B ничего не сохраняет, поэтому ссылка на UI-C может вести только к отдельному примеру. «Редактировать план» открывает [автономный демопрототип UI-E](../manual-scheduling-prototype.html) с разрешённой обратной ссылкой на UI-C; записи нет. Меню не содержит действующих команд записи. Деталь операции — read-only `<dialog>` с возвратом фокуса к вызвавшей кнопке.

На 1440–1280 px сводка имеет четыре карточки, свойства ТК — четыре колонки, операции — таблицу. На 1024 px и уже операции показаны карточками с теми же полями. На 767 px скрыта только статическая боковая оболочка; контент остаётся в одном вертикальном потоке. Таблица не требует горизонтального скролла страницы.

## Календарные зависимости и статусы

«Закупка материалов» и «Дизайн» показаны отдельными параллельными ветвями, которые сходятся перед «Печатью»; далее последовательно «Раскрой → Пошив → Упаковка». На mobile те же ветви и последовательность идут вертикально. Граф подписан как календарный; исходный маршрут ТК показан отдельным полем и не переписывается. Планировать дату следующей операции можно заранее. Основной календарный статус: не запланировано, запланировано, готово к запуску, в работе, приостановлено, завершено. Закупка — ручное подтверждение готовности материалов; часовой нормы нет.

`launchEligibility(row, rows)` даёт **индикацию**, а не разрешение серверного действия. Сначала учитывается собственный статус операции: завершённую и работающую не предлагают запускать повторно, приостановленную не называют доступной, отсутствие плана показывают явно. Затем для запланированной или готовой по календарю операции проверяются все обязательные предшественники: незавершённые дают отдельную причину блокировки. Если предшественники завершены, UI сообщает: «Предшественники завершены; фактический запуск проверяется сервером». Для «Готово к запуску» добавляется уточнение «Готово по календарю». Прототип не знает прав пользователя, действующей смены, фактических ресурсов, расхождений источника и серверных переходов. Цвет сопровождается текстом. Один результат функции используется в графе, таблице, мобильных карточках и диалоге; перегрузка, нулевая мощность, отсутствие нормы и просрочка остаются отдельными показателями.

## Расчёт и исключения

Демонстрационный снимок пошива: `360 с × 1 + 240 с × 2 = 840 с` на изделие для одной швеи; `840 × 100 = 84 000 с = 23,33 человеко-часа` на заказ. Демомощность `5 швей × 8 ч × 1 смена × 100% = 40 ч` на плановый день, загрузка `58%` после округления. В сценарии перегрузки `2 швеи × 8 ч × 1 смена × 100% = 16 ч`, `146%`. Исправлено прежнее отображение мощности как `0,01 ч`: часы не переводятся из секунд повторно. Процент не означает готовность изделий. При нулевой мощности процент не вычисляется. При неподтверждённой норме выводится «Нагрузка не рассчитана», без подстановки 0 ч или 0%. Для дизайна, печати, раскроя и упаковки подтверждённых норм нет: числовая трудоёмкость не выдумана. Для закупки часовую загрузку не показывать.

| Демосценарий | Проверяемое состояние |
|---|---|
| Дизайн в работе | Закупка завершена; печать запланирована, но запуск ждёт дизайн. |
| Печать готова по календарю | Оба корня завершены; печать готова по календарю, но фактический запуск проверяет сервер; раскрой ждёт её завершения. |
| Просрочка и перегрузка | Дизайн приостановлен и просрочен; печать блокирована зависимостью. Отдельно показана перегрузка пошива. |
| Нет нормы | Трудоёмкость и процент неизвестны. |
| Нулевая мощность | Трудоёмкость известна, доступно 0 ч; процент не выводится. |
| Нет маршрута | Операции не формируются, показана причина. |
| Пустой план | Нет дат и операций; показано пустое состояние. |

Сводка `1/6` или `2/6` считает **завершённые операции**, а не долю изготовленных изделий. Ответственный не показан: подтверждённого источника данных для этой роли в UI-C нет. При длинных значениях текст переносится; статус сопровождается текстом, а не одним цветом.
