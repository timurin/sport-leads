Выделить редактирование календарных записей без записи в исходные модели, техкарты или маршрут. **Артефакт:** `screens/production-order.md`. **Приёмка:** планирование будущей операции допустимо, фактический «Начать» заблокирован до завершения всех предшественников.

**PC-UI-07 — UI-D: детали дня и участка.** Мощность/занятость/резерв, задачи с указанием *нагрузки именно на выбранный день*, многодневные операции, фильтры, переход к заказу, перенос, доступные действия. Не обещать точную почасовую раздачу 8 швей из одной суммарной нормы, пока не определено распределение по бригадам. **Артефакт:** `screens/section-day.md`. **Приёмка:** сумма дневных назначений совпадает с KPI; превышение нормы видно без маскировки.

**PC-UI-08 — UI-E: ручное планирование.** Слева очередь незапланированных **операций** заказа (не дубли целого заказа на каждый участок), справа матрица участок×дата, назначение/перенос/удаление, операции на несколько дней, подтверждение сохранения, undo/cancel, проверки конфликтов. Drag-and-drop — дополнительный метод; обязательно доступная альтернатива через кнопки и модальное назначение дат на touch/mobile. **Артефакт:** `screens/manual-planning.md`. **Приёмка:** одна операция на 14 ч распределяется 8+6 ч без создания второй операции; сохранение не запускает исполнение.

**PC-UI-09 — UI-F: мощности и календарь исключений.** Настройки швей/смен/часов/коэффициента для пошива, рабочая неделя, исключения на конкретные даты (отпуска, 6 вместо 8 швей, выходной, дополнительная смена). Демонстрация формулы `N × H × смены × K`, деление на норму времени одной единицы из модели только для пошива; прочим участкам не подставлять эту норму. **Артефакт:** `screens/capacity-settings.md`. **Приёмка:** 0 швей или выходной дают 0 доступных часов; изменения нормы модели не меняют бесконтрольно уже зафиксированный план; никакой дублирующей нормы модели.

**PC-UI-10 — UI-G: Дашборд производственного календаря.** KPI периода, план/мощность/резерв отдельно по ресурсам, дневная/недельная динамика и drill-down к участку/дате без строк всех операций по умолчанию. **Артефакт:** `screens/gantt.md` и сохранённый путь `gantt-prototype.html`. **Приёмка:** 5/30/50/100 синтетических заказов, unknown/zero и независимые ресурсные единицы; OWNER-APPROVED 2026-10-05 по задаче design freeze.

**PC-UI-11 — UI-H: Центр отклонений.** Агрегированные группы причин, уникальные затронутые заказы и сигналы отдельно, общий конфликт ресурса/даты одним случаем с полным списком участников, поиск/фильтры/сортировка/пагинация/детали. **Артефакт:** `screens/risks-conflicts.md`. **Приёмка:** hard/risk/unknown раздельны, фильтр не удаляет события, 100 заказов без бесконечного журнала; OWNER-APPROVED 2026-10-05 по задаче design freeze.

**PC-UI-12 — Сквозной UX, состояния, доступность и согласование.** Описать сценарий: создать заказ → получить операции → вручную назначить закупку/дизайн → печать/раскрой/пошив/упаковку → увидеть нагрузку и конфликт → перенести → завершить этап → разблокировать следующий. Для всех экранов: empty/loading/error/permission/validation, keyboard focus, contrast, responsive, отсутствие горизонтальной прокрутки *всей страницы* (допустима внутренняя прокрутка широких сеток), единые статусы и подписи. **Артефакт:** `docs/design/production-calendar/review-checklist.md` + итоговый индекс `README.md` со ссылками на 8 спецификаций. **Приёмка:** все состояния и переходы описаны, несогласованные вопросы перечислены, получено явное пользовательское «дизайн утверждён» **до любой реализации**.

### 3.4. Сквозные архитектурные ограничения дизайна

1. Календарный заказ автономен; отсутствие ведения заказов покупателей в CRM — штатный сценарий.
2. Все реальные справочники переиспользуются **по подтверждённым контрактам**; новые поля `Количество/Время` для модели не создавать.
3. Норма пошива: время на **одно изделие на одну швею**; в календаре дневная доступность = число доступных швей × часы × число смен × эффективность, единицы конвертировать явно.
4. «Закупка» и «Дизайн» идут параллельно и обе завершаются до старта печати. Планировать следующие операции заранее можно; «Начать» — только после предшественников с серверной проверкой при будущей реализации.
5. Для остальных участков отдельно подтверждать источник нормы и ресурсную метрику. «Нет данных» показывать явным состоянием, а не делать вид, что загрузка 0%.
6. План остаётся ручным; интерфейс не подразумевает авторазмещение, автоматические закупки, списание запасов, расчёт себестоимости и переписывание статусов CRM.
7. При визуализации различать: цвет конкретного участка, цвет статуса выполнения и предупреждение о перегрузке. Не кодировать все три смысла одним цветом без текста/иконки.
