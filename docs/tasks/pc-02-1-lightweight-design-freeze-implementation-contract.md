# PC-02.1 — Lightweight Design Freeze & Implementation Contract

## Контекст
Production Calendar v0.1 спроектирован как лёгкий диспетчерский инструмент для формирования очереди и загрузки производства, а не как MES/APS.

UI-A–UI-H согласованы владельцем. UI-G трактуется как «Дашборд производственного календаря», UI-H — «Центр отклонений». Основная ежедневная работа должна занимать минимум времени и опираться на уже существующие данные ERP.

## Цель
Зафиксировать дизайн и подготовить минимальный контракт для начала PC-03 без реализации backend/frontend.

## Сделать
1. Зафиксировать в roadmap/specs:
   - UI-A–UI-H = OWNER-APPROVED;
   - общий DESIGN-APPROVED = true;
   - UI-G переименовать концептуально из Gantt в Dashboard во всей документации;
   - UI-H = Центр отклонений;
   - PC-02.1 закрыть после выполнения этой задачи.

2. Зафиксировать принцип v0.1:
   - минимум ручного ввода;
   - максимум данных брать из существующих заказов, ТК, моделей, ресурсов и норм;
   - не создавать отдельные сущности/статусы/справочники без необходимости;
   - календарь нужен для очереди, дат, загрузки и простых предупреждений;
   - UI-G/H — обзор и контроль, а не обязательный ежедневный workflow.

3. Проверить существующие модели проекта и определить только минимально необходимые новые сущности/поля для Production Calendar.
   Для каждой новой сущности указать:
   - зачем она нужна;
   - почему нельзя использовать существующую;
   - минимальный набор полей.
   Не проектировать «на будущее».

4. Зафиксировать минимальный implementation contract PC-03:
   - какие существующие сущности переиспользуются;
   - какие новые сущности действительно нужны;
   - минимальные API endpoints;
   - минимальные frontend routes/components;
   - как связаны UI-A, UI-C, UI-D, UI-E, UI-F, UI-G, UI-H;
   - какие проверки блокируют запуск операции, а какие только предупреждают.

5. Разбить PC-03 на короткие последовательные подэтапы:
   - persistence/data model;
   - API;
   - weekly board;
   - manual scheduling;
   - capacity/read-only calculations;
   - dashboard/deviations;
   - integration/tests.

## Ограничения
- Не писать реализацию PC-03.
- Не менять приложение, API, модели и миграции.
- Не исправлять P1 refresh-model в этой задаче.
- Не добавлять сложный auto-scheduling, optimizer, solver, workflow engine, отдельный MES-контур.
- Не вводить обязательные поля, которые диспетчер должен заполнять вручную, если данные уже есть в ERP.
- Не создавать дублирующие справочники сотрудников, оборудования, участков, моделей, ТК и заказов.
- Сохранить DS-SHELL-01/02 и утверждённые UI-A–UI-H.

## Проверки
- Markdown roadmap и HTML twin синхронизированы.
- UI-G нигде в пользовательской терминологии не называется Gantt.
- OWNER-APPROVED отмечен для UI-G/H.
- DESIGN-APPROVED закрыт.
- Новый implementation contract не содержит избыточных сущностей.
- git diff --check.

## Результат
Краткий отчёт:
1. Что закрыто.
2. Какие существующие сущности переиспользуются.
3. Какие новые сущности нужны и почему.
4. План PC-03 по коротким подэтапам.
5. Какие вопросы/риски остаются открытыми.

Commit/push не выполнять.
