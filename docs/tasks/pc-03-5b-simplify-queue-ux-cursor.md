# PC-03.5B — Simplify Production Queue UX

## Контекст
Модуль: Production Calendar / «Очередь производства».
Работа выполняется параллельно с Codex PC-03.5A.
Cursor меняет только frontend.

Текущая форма «Добавить работу» перегружает менеджера производственными решениями:
- поиск и отдельный select ТК дублируют друг друга;
- выбор участка на момент постановки заказа некорректен;
- ручная «Позиция в очереди» не имеет смысла для менеджера.

## Цель
Сделать постановку заказа в производственную очередь максимально простой.

## 1. Навигация
В левом меню раздел «Производство» привести к структуре:

- **Производственный календарь**
  - Ручное планирование
  - Мощности
  - Дашборд
  - Центр отклонений

То есть текущий родительский пункт «Очередь производства» переименовать в:
**Производственный календарь**

Основной маршрут родителя остаётся текущим экраном недельной очереди.

Не менять дизайн sidebar и его visual contract.

## 2. Модальное окно «Добавить работу»

### Убрать
- отдельное поле «Участок»;
- поле «Позиция в очереди»;
- отдельную связку «Поиск ТК / заказа» + независимый select «Техническая карта».

### Сделать один понятный поиск ТК/заказа
Использовать searchable combobox/autocomplete.

Поле:
**Техническая карта / заказ**

Placeholder:
`Начните вводить номер ТК или заказа`

При вводе показывать состояния:
- «Ищем…»
- найденные результаты;
- «ТК не найдена»;
- при отсутствии результата — существующая ссылка/действие для создания standalone ТК.

Каждый найденный вариант должен быть понятным:
- номер ТК;
- связанный заказ, если есть;
- наименование/клиент, если данные уже доступны существующим API.

После выбора результат должен быть явно зафиксирован в форме.
Не оставлять рядом второй select с теми же данными.

### Оставить
- выбранная ТК / заказ;
- дата постановки в очередь;
- примечание (необязательное).

Стартовая стадия назначается backend автоматически и не редактируется менеджером.

## 3. Текст/UX
Менеджер должен понимать действие как:
**«Поставить заказ в производственную очередь»**

Не требовать знания:
- конкретного производственного участка;
- позиции среди других заказов;
- будущего маршрута заказа.

Основной CTA:
**Добавить в очередь**

## 4. Интеграция
Использовать контракт Codex PC-03.5A.
Если backend ещё не готов, UI можно собрать на текущих типах, но не придумывать новый frontend-only workflow.

## Не делать
- не менять backend/API/DB;
- не реализовывать автоматические переходы стадий на frontend;
- не менять мощности;
- не менять dashboard/центр отклонений;
- не делать commit/push/merge.

## Тесты
Проверить:
- структура меню;
- основной маршрут «Производственный календарь»;
- autocomplete/search states;
- выбор ТК;
- empty/not-found state;
- отсутствие полей «Участок» и «Позиция в очереди»;
- submit с минимальным payload;
- error/loading states.

## Проверки
- targeted frontend tests;
- full frontend tests;
- npm run lint;
- npx tsc --noEmit;
- production build;
- git diff --check.

## Acceptance
Постановка заказа должна занимать:
1. найти/выбрать ТК;
2. выбрать дату;
3. при необходимости написать примечание;
4. нажать «Добавить в очередь».

Никаких производственных решений менеджер в этой форме не принимает.
