# PC-03.6B — Weekly Board Visual Redesign

## Контекст
Текущий Production Calendar на платформе визуально сильно отличается от утверждённого `weekly-board-prototype.html`.

Утверждена новая концепция отображения:
- строки = стадии;
- колонки = дни;
- заказ = компактный стикер;
- длина стикера = длительность операции;
- цвет = стадия;
- клик по стикеру открывает большую modal ТК в read-only;
- показывать все заказы, выполняющиеся в этот день;
- будущую механику очереди пока не менять.

Эта задача выполняется параллельно с Codex PC-03.6A.
Cursor меняет только frontend.

## Цель
Привести Production Calendar к утверждённому визуальному стилю `weekly-board-prototype.html` и упростить восприятие заказов.

## 1. Внешний вид страницы
Основой считать утверждённый `weekly-board-prototype.html`.

Нужно приблизить production page к прототипу:
- плотность;
- размеры;
- spacing;
- заголовок;
- toolbar;
- карточки/стикеры;
- сетка календаря;
- типографика;
- адаптив.

Не менять общий AppShell платформы.

## 2. Навигация

### Левое меню
В разделе «Производство» оставить только один пункт:

**Производственный календарь**

Убрать постоянные подпункты:
- Ручное планирование;
- Мощности;
- Дашборд;
- Центр отклонений.

### Toolbar страницы
Перенести туда:
- Календарь;
- Ручное планирование;
- Мощности;
- Дашборд;
- Центр отклонений.

Активное состояние текущего экрана должно быть понятно.

## 3. Новый вид assignment
В календарной сетке не показывать большую карточку с действиями.

Показывать компактный стикер:
- текст по умолчанию только номер, например `1760/1`;
- одна строка;
- дружелюбный компактный вид;
- цвет зависит от стадии;
- цвета только мягкие/pastel, без пестроты.

Предлагаемая семантика цвета:
- Подготовка к запуску — нейтральный серо-фиолетовый;
- Дизайн — светло-синий;
- Печать — мягкий янтарный;
- Раскрой — приглушённый зелёный;
- Пошив — мягкий сиренево-розовый;
- ВТО и Упаковка — голубовато-серый;
- Контроль качества — нейтральный зелёный;
- Готовы к отгрузке — светло-зелёный;
- красный только для реальной проблемы/просрочки.

Не использовать яркие saturated цвета.

## 4. Диапазон дат
Использовать контракт PC-03.6A:
- `planned_start_date`;
- `planned_end_date`.

Если backend ещё не готов во время frontend-разработки:
- использовать typed mock/fixture с тем же контрактом.

Стикер должен визуально тянуться на весь диапазон операции, аналогично календарю Bitrix24:
- один assignment = одна полоска;
- полоска проходит через несколько дней;
- при переходе недели корректно обрезается на границах текущего view.

Не дублировать один и тот же assignment отдельной карточкой в каждом дне.

## 5. Быстрое понимание состояния заказа
Менеджер должен за 2–3 секунды понять:
- где находится заказ;
- на какой стадии;
- до какого дня идёт текущая операция;
- когда заказ планово будет готов, если финальная дата уже известна.

Не перегружать ячейки текстом.

Убрать постоянные служебные надписи:
- `Недостаточно данных`;
- `Есть резерв 0%`;
- `По ресурсам ...`.

Load-state оставить только компактным индикатором/tooltip/popover.

## 6. Все заказы
Показывать все assignment, активные в конкретный день.

Не делать `+ ещё N` по умолчанию.
Не прятать список во внутренний scroll, если можно расширить высоту строки/раскладки естественно.

Важно:
- визуально не превращать день в набор больших карточек;
- использовать компактные полоски/стикеры.

## 7. Click → Technical Card modal
Клик по `1760/1` открывает большую modal ТК в режиме просмотра.

Modal должна использовать существующие данные/компоненты техкарты, если возможно.

Показать read-only:
- номер ТК/заказа;
- клиент/наименование, если доступно;
- количество;
- текущую стадию;
- плановые даты;
- материалы;
- размеры;
- персонализацию;
- примечания;
- ссылку `Открыть техкарту`.

Не дублировать полноценную форму редактирования.

## 8. Не менять create/edit flow
Эта задача только про display/UX.

Не менять:
- create modal PC-03.5;
- backend;
- DB;
- автоматическую стартовую стадию;
- auto-position;
- UI-E business logic;
- capacity logic.

## 9. Tests
Минимум:
- toolbar navigation;
- left menu only `Производственный календарь`;
- single-day sticker;
- multi-day sticker;
- week-boundary clipping;
- multiple assignments in same stage/day;
- pastel stage styles;
- load-state compact display;
- click opens TK read-only modal;
- modal closes correctly;
- no duplicated assignment per day.

## Проверки

- full frontend tests;
- npm run lint;

- git diff --check;
- project check.

## Acceptance
Готово, если недельный календарь визуально близок к утверждённому `weekly-board-prototype.html`, а менеджер может быстро определить:
- номер заказа;
- текущую стадию;
- длительность операции;
- плановую готовность, если она известна.
