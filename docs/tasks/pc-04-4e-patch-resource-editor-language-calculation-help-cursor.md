# PC-04.4E PATCH — Resource Editor Language & Calculation Help

## Исполнитель
Cursor

## Контекст
Маршрут:
`/settings/catalogs/tech-operations`

В modal редактирования ресурса многие поля и значения непонятны пользователю:
- `Тип ресурса`
- `Режим расчёта`
- `Базовая норма`
- `Количество ресурсов`
- `Эффективность`
- `Веха`

Нужно сделать форму понятной без знания внутренних кодов backend.

Backend contract не менять.
Технические enum/code остаются прежними, меняются UI labels/help.

---

# 1. Переименовать поле `Тип ресурса`

Текущее:
`Тип ресурса`

Новое:
**`Вид ресурса`**

UI labels enum:

- `labor` / трудовой -> **Персонал**
- `team` -> **Бригада**
- `machine` / equipment -> **Оборудование**
- `milestone` -> **Контрольная точка**

Для `Контрольная точка` helper:
`Этап не резервирует производственную мощность и используется как контрольное событие процесса.`

Не показывать пользователю слово `Веха`.

---

# 2. Переименовать и пояснить основные поля

## `Единица мощности`
Новый label:
**`В чём измеряется загрузка`**

Helper examples:
- чел.-ч — труд сотрудников;
- шт. — количество изделий;
- м.п. — погонные метры;
- маш.-ч — время оборудования.

---

## `Режим расчёта`
Новый label:
**`Как рассчитывается потребность`**

Business labels:

- `rate` -> **По производительности**
- `sewing_norm` -> **По норме пошива модели**
- `cutting_methods` -> **По способу раскроя**
- `team_rate` -> **По производительности бригады**
- `explicit_hours` -> **По заданной норме времени**
- `milestone` -> **Без расчёта мощности**

Технический код можно показывать только в tooltip/debug.

---

## `Базовая норма`
Не использовать один label для всех режимов.

Label должен зависеть от calculation mode.

### rate
**`Производительность в час`**

### team_rate
**`Производительность бригады в час`**

### explicit_hours
**`Норма времени`**

Helper:
`Используется только если потребность ТК действительно задаётся нормой времени.`

### milestone
Поле скрыть.

### sewing_norm
Поле скрыть, если норма приходит из модели/варианта сборки.

### cutting_methods
Не показывать одно поле `Базовая норма`.
Показывать отдельные методы/ставки.

---

# 3. `Количество ресурсов`

Сделать label динамическим.

### Персонал
**`Количество сотрудников`**

### Бригада
Если производительность задана на всю бригаду:
**не показывать multiplier как численность**, если backend contract использует resource_count=1.

Показывать helper:
`Производительность указана для всей бригады.`

### Оборудование
Если WorkCenter = конкретная машина:
поле скрыть.

Одна запись WorkCenter = одна физическая машина.

Не показывать `Количество ресурсов = 1` как обязательное поле.

---

# 4. `Часов в день`

Новый label:
**`Рабочих часов в день`**

Helper:
`Сколько часов ресурс доступен в обычный рабочий день.`

Не подставлять значение по умолчанию.

---

# 5. `Смен в день`

Оставить:
**`Смен в день`**

Helper:
`Используется при расчёте доступной мощности за день.`

Если для конкретного типа ресурса shifts не применяется — скрыть.

---

# 6. `Эффективность`

Новый label:
**`Коэффициент эффективности`**

Рядом отображать человекочитаемое значение:

- 1.00 → `100%`
- 0.90 → `90%`
- 0.85 → `85%`

Helper:
`Учитывает плановые потери рабочего времени. 1,00 = 100%.`

Если UX позволяет, предпочтительно показывать процентный input,
но сохранять backend value в текущем формате.

Не менять API contract.

---

# 7. Checkbox

Текущее:
`Учитывать в загрузке календаря`

Новое:
**`Учитывать при планировании`**

Helper:
`Если выключено, Scheduler не резервирует мощность этого ресурса.`

---

# 8. Новый блок `Как считается`

В modal ресурса добавить компактный read-only блок:

## Как считается

Он должен динамически показывать формулу и короткий пример
на основе текущего вида ресурса / режима.

Это только UI help.
Не использовать этот блок как альтернативный Scheduler calculation engine.

---

# 9. Примеры для Персонала

Например ресурс:
`Швеи`

Поля:
- количество сотрудников: 5
- рабочих часов: 10
- эффективность: 90%

Показать:

**Доступная мощность**
`5 сотрудников × 10 ч × 90% = 45 чел.-ч/день`

Ниже:
`Если заказ требует 30 чел.-ч, он займёт примерно 0,67 рабочего дня при полностью свободном ресурсе.`

Последняя строка — helper/пример, не фактический scheduler forecast.

---

# 10. Пример для раскроя

Если calculation mode = `cutting_methods`:

Показать:

**Поштучный раскрой**
`20 шт./чел.-ч`

Пример:
`Заказ 100 шт. → требуется 5 чел.-ч.`

**Раскрой настилом**
`40 шт./чел.-ч`

Пример:
`Заказ 100 шт. → требуется 2,5 чел.-ч.`

Quantity в примере можно использовать фиксированное демонстрационное `100 шт.`,
с явной подписью:
`Пример`.

Не брать текущую ТК — это settings modal.

---

# 11. Пример для Бригады

Например:
`Бригада упаковки`

- 80 шт./ч
- 10 часов

Показать:

**Доступная мощность**
`80 шт./ч × 10 ч = 800 шт./день`

Helper:
`Норма задана для всей бригады, а не для одного сотрудника.`

---

# 12. Пример для Оборудования

Например WorkCenter:
`Epson SC-F9200`

- 15 м.п./ч
- 10 часов
- efficiency 90%

Показать:

**Доступная мощность**
`15 м.п./ч × 10 ч × 90% = 135 м.п./день`

Helper:
`Scheduler резервирует загрузку конкретного WorkCenter.`

Если WorkCenter source of truth:
не дублировать editable rate/hours внутри TechOperation resource card.

---

# 13. Пример для `explicit_hours`

Показать предупреждение:

**По заданной норме времени**

`Для расчёта ТК должна существовать отдельная норма, определяющая сколько часов требует операция.`

Если Demand rule отсутствует:
показать readiness warning:

`Не настроено правило расчёта потребности`

Не создавать формулу из Capacity полей.

Это особенно важно для:
- ВТО;
- дизайна;
- оператора печати.

Показать:

# 15. Разделить `Потребность` и `Мощность` визуально

В modal добавить два небольших смысловых блока.

## Как определяется потребность заказа
Например:
`Из нормы пошива модели`
или
`Из количества × способ раскроя`
или
`Из объёма печати`

## Как определяется доступная мощность
Например:
`5 сотрудников × 10 ч × 90%`
или
`15 м.п./ч × 10 ч`

Цель:
пользователь должен видеть, что Demand и Capacity — разные вещи.

# 16. Tooltip `Что это?`

Для сложных полей добавить компактный `?` tooltip:

### Как рассчитывается потребность
`Определяет, откуда система получает объём работы для конкретной техкарты.`

### Рабочих часов в день
`Используется только для расчёта доступной мощности ресурса.`

### Производительность
`Сколько единиц ресурс способен выполнить за один час.`

### Коэффициент эффективности
`Плановая доля полезного рабочего времени.`

Технический reason оставить в tooltip/debug details.

# 18. Не менять бизнес-логику

Этот patch НЕ должен:
- менять Demand adapters;
- менять Capacity formula;
- менять Scheduler;
- создавать нормы;
- исправлять отсутствующие business rules;
- менять backend enum values.

Только:
- названия;
- conditional visibility;
- helper text;
- example calculations;
- layout.

Если текущий API не позволяет определить calculation mode/source —
зафиксировать `BACKEND GAP`, не придумывать.
