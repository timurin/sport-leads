# PC-04.4K — Tech Card Route Choice UX

## Исполнитель
Cursor

## Источник истины
Использовать текущие Routing Graph / ONE OF / Scheduler contracts и `docs/architecture/unified-routing-graph-pc-04-4g.md`.
Backend/runtime не менять.

## Цель
Упростить standalone TechnicalCard для менеджера:
- выбрать маршрут;
- увидеть короткую цветную схему;
- выбрать ONE OF вариант;
- увидеть ETA;
- увидеть рекомендацию более быстрого варианта, если backend уже даёт необходимые данные;
- запустить/пересчитать ТК без ввода человеко-часов, норм и capacity values.

## Изменения

### 1. Layout
Перенести `Маршруты и операции` вниз страницы, рядом с `План производства`.
Объединить в смысловой блок `Технологический процесс`.

### 2. Цветная схема
После выбора маршрута показать компактную графическую схему:
- parent = Цех;
- child = TechOperation;
- последовательность = стрелки;
- ONE OF = отдельный блок `Выполняется один вариант`;
- selected option = заметный акцент;
- recommended option = отдельный акцент;
- дата готовности = главный числовой акцент.

Использовать мягкие цветные карточки/чипы. Схема должна читаться за 3–5 секунд.

### 3. ONE OF
Показывать группу вариантов понятным списком, например:
- Ручной раскрой
- Раскрой настилом
- Раскрой лазером

Отображать selected/default/preliminary/confirmed по существующим API.

### 4. ETA
После выбора маршрута/варианта показывать:
- ожидаемую готовность;
- дату отгрузки;
- запас/риск, если уже есть в plan API.

Не считать ETA во frontend.

### 5. Recommendation
Если backend уже позволяет корректно сравнить альтернативные ETA, показать:
`Рекомендуем: <вариант>`
`Готовность на N дней раньше`.

Если данных недостаточно — `BACKEND GAP`, без client-side scheduling logic.

### 6. Убрать технические ошибки
Не показывать менеджеру raw codes:
- `missing_operator_norm`
- `manual_required`
- другие internal reasons.

Вместо:
`Маршрут требует настройки`
и понятная причина:
`Не настроена производственная норма операции «...». Обратитесь к администратору производства.`

Не показывать менеджеру ручной ввод чел.-ч/метров/норм/capacity.

### 7. Preliminary / Confirmed
Сохранить существующую semantics, но пояснить:
- `Предварительно` — используется для предварительного плана;
- `Подтверждено` — подтверждено производством.

### 8. Replan
После смены варианта использовать существующий flow:
`Вариант изменён. Для обновления календаря пересчитайте план.`
Кнопка `Пересчитать план`.

После расчёта обновить ETA и deadline state.

### 9. Визуальный приоритет
1. маршрут;
2. схема;
3. вариант;
4. ETA;
5. рекомендация;
6. вторичные статусы.

### 10. Не менять
Не менять:
- backend;
- Scheduler;
- Demand;
- Capacity;
- WorkCenter;
- snapshot;
- Routing runtime;
- VIS-STRESS.

## Tests

- маршрут с ONE OF;
- preliminary;
- confirmed;
- route not ready;
- human-readable blocker;
- replan;
- ETA;
- recommendation только если реально поддерживается API.

Full:

## Acceptance
Менеджер без знания производственных норм может:
1. выбрать маршрут;
2. понять схему процесса;
3. выбрать вариант;
4. увидеть ожидаемую дату готовности;
5. увидеть рекомендацию, если её поддерживает backend;
6. запустить/пересчитать ТК без технического ручного ввода.
