# PC-04.4R — Inline Readiness Error Highlighting

## Исполнитель
Cursor

## Контекст
В modal редактирования TechOperation diagnostic уже показывается под заголовком, но визуально слабый и не указывает явно, где именно ошибка.

Пример:
`Операция «Подготовка макетов»: не заполнено поле «Правило расчёта потребности».`

Backend diagnostics PC-04.4M/4Q считать source of truth.
Backend не менять.

## Цель
Сделать ошибку визуально очевидной:
1. контрастный diagnostic под заголовком;
2. подсветка конкретного поля/блока, к которому относится diagnostic;
3. переход к нужной вкладке/полю по клику.

## Сделать

### 1. Diagnostic в header
Под заголовком modal показывать compact alert:
- blocking/error → красный фон/бордер/иконка;
- warning → оранжевый;
- текст backend `message`;
- если ошибок несколько — первая + `Ещё N`.

### 2. Подсветка конкретного места
Использовать diagnostic metadata:
- `field`
- `entity_type`
- `entity_id`
- `fix_scope`

Связать diagnostic с конкретным UI field/section.

Примеры:
- `Правило расчёта потребности` → блок `Как считается` / Demand rule;
- `Норма времени` → поле нормы;
- `Рабочих часов в день` → поле часов;
- `Производительность` → поле производительности;
- `Оборудование` → вкладка/блок оборудования.

Проблемное поле:
- красный border;
- мягкий red background;
- inline helper/error text.

### 3. Навигация к ошибке
- ошибка на другой вкладке → badge на вкладке;
- клик по alert → открыть нужную вкладку и scroll/focus на поле;
- при первом открытии modal можно автоматически открыть вкладку первой blocking-ошибки;
- не мешать пользователю после начала редактирования.

### 4. Ошибка уровня блока
Если diagnostic относится к целому правилу, а не к одному input:
- подсветить section/card;
- показать внутри `Требует настройки: <причина>`.

### 5. После исправления
После save/revalidate:
- alert исчезает;
- подсветка исчезает;
- readiness обновляется;
- не хранить stale frontend error state.

### 6. Не дублировать
Допустимо одновременно:
- header alert;
- локальная подсветка поля/блока.

Не оставлять ещё один большой warning внизу формы с тем же текстом.

## UX
Пользователь за 1–2 секунды должен понять:
- что сломано;
- где это находится;
- какое поле нужно заполнить.

## Не менять
- backend;
- diagnostic texts/codes;
- Demand/Scheduler;
- Capacity;
- Routing;
- VIS-STRESS.

## Tests
Проверить:
- ошибка на текущей вкладке;
- ошибка на другой вкладке;
- field-level diagnostic;
- section-level diagnostic;
- несколько diagnostics + `Ещё N`;
- click → tab/focus;
- save → error disappears;
- no duplicate warnings.

Full:
- frontend tests;
- eslint;
- tsc;
- production build;
- project check;
- git diff --check.

## Acceptance
Готово, если:
1. ошибка под заголовком визуально контрастная;
2. конкретное проблемное поле/блок подсвечено;
3. клик по ошибке ведёт к месту исправления;
4. ошибки на других вкладках видны badge;
5. после исправления подсветка исчезает;
6. backend не менялся.

Финальная строка:
`PC-04.4R INLINE READINESS ERROR HIGHLIGHTING READY FOR OWNER REVIEW`
