# PC-05.5 — Debug Log Download + Missing Operation Norms Modal

## Исполнитель
Cursor

## Цель
Добавить две UX-функции:

1. В глобальном Debug Mode — возможность скачать diagnostic log-файл для передачи на анализ.
2. После выбора модели в техкарте — если нормы операций модели не заполнены, сразу показать понятное модальное окно и не заставлять менеджера искать причину через Debug.

Использовать:
- `SL-PROJECT-MEMORY-v1`
- `SL-UI-CONTEXT-v1`
- только релевантные `DF-*`
- targeted frontend files only.

Не делать repo-wide scan.

---

# 1. Debug Mode — Скачать log

## UI
В модальном окне `Диагностика платформы` добавить кнопку:

`Скачать log`

Файл должен скачиваться локально пользователю.

Предпочтительный формат:
`JSON`

Допустимо дополнительно дать TXT, но JSON обязателен.

Имя файла, например:

`Sport-Leads-debug-2026-10-12T12-30-00.json`

## Что включать
Собрать текущие diagnostics из уже используемого `GET /platform-health` и текущего контекста Debug Center.

Минимум:

- generated_at;
- app/module/page context;
- current entity, если Debug открыт из конкретной страницы;
- active filters;
- diagnostics count;
- diagnostics array.

Для каждого diagnostic сохранить доступные поля:

- code;
- severity;
- category;
- module;
- entity_type;
- entity_id;
- entity_name;
- field;
- field_label;
- operation_id;
- snapshot_node_id, если backend отдаёт;
- resource_key;
- reason;
- expected_source;
- source_value;
- actual_value;
- fix_scope;
- fix_url;
- trace / lineage;
- technical details payload.

## Безопасность
НЕ включать:
- access/refresh tokens;
- cookies;
- Authorization headers;
- passwords;
- DB connection strings;
- secrets/.env;
- персональные session credentials.

Перед экспортом использовать whitelist разрешённых diagnostic fields, а не dump всего runtime state.

## Важно
Log должен содержать исходные technical diagnostics, а не только manager-facing текст.

Это нужно, чтобы владелец мог скачать файл и передать его для анализа.

# 2. TechnicalCard — проверка норм сразу после выбора модели

## Проблема
Сейчас модель можно выбрать, даже если у неё отсутствуют нормы операций, а ошибка обнаруживается позже через Demand/Scheduler.

Нужно ловить это сразу после выбора модели.

## Trigger
После выбора/смены модели в TechnicalCard проверить, заполнены ли обязательные нормы операций выбранного model route variant.

Использовать существующий model/route/norm contract.

Не придумывать отдельную frontend readiness logic, если backend уже отдаёт model readiness/diagnostics.

Если backend не предоставляет достаточные данные:
зафиксировать точный `BACKEND GAP` и не дублировать сложную бизнес-логику во frontend.

## Что считать ошибкой
Если для активного/выбранного варианта маршрута есть операция, которая требует норму на 1 изделие, но её значение отсутствует/пустое.

Не считать ошибкой:
- операции, которым по contract норма не требуется;
- milestone;
- другие явно exempt операции согласно существующей архитектуре.

# 3. Modal

При обнаружении отсутствующих норм показать модальное окно:

## Title
`Нормы операций не заполнены!`

## Message
`Для выбранной модели не заполнены нормы одной или нескольких производственных операций. Без них техкарта не может быть корректно рассчитана и запланирована.`

По возможности ниже коротко перечислить проблемные операции, например:

- Сублимационная печать
- Термоперенос

Не показывать technical codes менеджеру.

## Buttons

### Для обычного пользователя
- `Закрыть`

### Для администратора
- `Закрыть`
- `Заполнить`

`Заполнить` должно открывать правильный экран модели / вариант маршрута / нормы операций, где эти значения реально редактируются.

Не вести администратора на общий список, если можно открыть конкретную модель.

---

# 4. Поведение после модального окна

После `Закрыть`:
- модель может остаться выбранной;
- ТК должна явно иметь состояние `Требует настройки`;
- планирование не должно казаться доступным/готовым, если backend readiness уже блокирует его.

Не очищать выбранную модель автоматически.

После `Заполнить`:
- открыть страницу/секцию редактирования норм;
- после возврата/refresh повторно проверить readiness.

---

# 5. Роли

Кнопка `Заполнить` доступна только пользователю с правом администрирования/редактирования соответствующего справочника.

Использовать существующую permission model.

Не проверять роль только по тексту `admin` на frontend, если есть canonical permissions.

---

# 6. Связь с текущим случаем SKU 201.1

Проверить сценарий:

- выбрать модель SKU `201.1`;
- если нормы отсутствуют → modal появляется сразу;
- после заполнения норм и повторной проверки modal больше не появляется;
- если существующая ТК была создана до заполнения норм, отсутствие copied snapshot norm остаётся отдельным DATA_FLOW diagnostic и не маскируется этим modal.

Важно:
modal решает раннее обнаружение отсутствующих model norms, но НЕ подменяет snapshot/reapply semantics.

# 7. Tests

## Debug log
- кнопка видна только в Debug Mode;
- JSON скачивается;
- diagnostics присутствуют;
- current context присутствует;
- secrets отсутствуют;
- empty diagnostics export корректен.

## Norm modal
- модель с заполненными нормами → modal не появляется;
- модель без норм → modal появляется;
- обычный пользователь → только `Закрыть`;
- администратор → `Закрыть` + `Заполнить`;
- `Заполнить` ведёт на правильную модель/раздел;
- после заполнения и refresh modal исчезает;
- manager-facing текст без technical terminology.

## Full
- frontend tests;
- eslint;
- tsc;
- production build;
- project check;
- git diff --check.

# Ограничения

Не менять:
- Demand semantics;
- Scheduler;
- route snapshot logic;
- Capacity/WorkCenter;
- production facts;
- stress data.

Если для проверки model norms не хватает backend contract:
не писать сложную duplicate-валидацию во frontend.
Дать точный `BACKEND GAP`.

Commit/push не выполнять.
