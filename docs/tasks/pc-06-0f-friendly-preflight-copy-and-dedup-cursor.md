# PC-06.0F — Friendly Preflight Copy + Deduplicate Operation Errors

## Исполнитель
Cursor

## Цель
Улучшить тексты в модальном окне `Техкарта требует настройки`, чтобы менеджер без технических знаний сразу понимал:

- что именно не заполнено;
- где это исправить;
- к какой операции относится ошибка;
- какие ошибки повторяются и могут быть объединены.

Бизнес-логику readiness/diagnostics не менять.

---

## 1. Сделать тексты дружелюбными

Не использовать технические формулировки вроде:

- `Не указан метраж для производственной операции`
- `Производственный план требует проверки или пересчёта`
- `В сборке изделия не заполнены обязательные данные`

Заменить на понятные manager-facing формулировки.

### Примеры

#### Сборка
Было:
`В сборке изделия не заполнены обязательные данные`

Стало:
**Нужно заполнить параметры сборки**

Описание:
`Для сборки «Пошив футболки» не заполнено: норма пошива.`

Подсказка:
`Откройте сборку изделия и заполните недостающие параметры.`

Button:
`Открыть сборку`

---

#### Метраж операции
Было:
`Не указан метраж для производственной операции.`

Стало:
**Не указана норма расхода для операции «Сублимационная печать»**

Описание:
`Для расчёта этой операции нужно указать расход на одно изделие.`

Подсказка:
`Откройте нормы модели и заполните метраж для операции «Сублимационная печать».`

Button:
`Заполнить норму`

То же для:
`Термоперенос`

---

#### План
Было:
`Производственный план требует проверки или пересчёта.`

Стало:
**Производственный план нужно пересчитать**

Описание:
`После изменений в техкарте сохранённый план больше не актуален.`

Подсказка:
`Проверьте даты и заново рассчитайте производственный план.`

Button:
`Пересчитать план`

---

#### Даты
Было:
`Не заполнены даты планирования и отгрузки`

Стало:
**Укажите даты производства и отгрузки**

Описание:
`Без даты начала и даты отгрузки система не сможет рассчитать производственный план.`

Button:
`Указать даты`

---

#### Нормы операций
Было:
`Не заполнены нормы операций`

Стало:
**Нужно заполнить нормы производственных операций**

Описание:
`Для следующих операций нет норм:`

- Сублимационная печать
- Термоперенос

Подсказка:
`Откройте нормы модели и заполните значения для этих операций.`

Button:
`Заполнить нормы`

---

## 2. Всегда показывать название операции

Если diagnostic относится к конкретной operation/snapshot node, UI должен показывать её название.

Не показывать две одинаковые карточки:

`Не указан метраж...`
`Не указан метраж...`

без пояснения.

Должно быть либо:

**Не указана норма расхода**
- Сублимационная печать
- Термоперенос

либо отдельные карточки:

**Сублимационная печать — не указана норма расхода**
**Термоперенос — не указана норма расхода**

Предпочтение: объединять одинаковые ошибки одного типа в одну карточку со списком операций.

---

## 3. Deduplication

Добавить presentation-layer grouping.

Группировать diagnostics, если совпадают:
- тип/код ошибки;
- fix_action/fix_url;
- severity;
- смысл исправления.

Не объединять ошибки, если исправляются в разных местах.

Пример:

Две ошибки `missing_linear_meters` для:
- Сублимационная печать
- Термоперенос

→ одна карточка:
**Нужно заполнить норму расхода**
`Не заполнено для 2 операций:`
- Сублимационная печать
- Термоперенос

---

## 4. Не дублировать плановые ошибки

На скриншоте одновременно появляются две карточки:

`Производственный план требует проверки или пересчёта`

Если это одна и та же причина/действие:
- показать одну карточку.

Если причины разные:
- объединить под одним заголовком;
- показать 2 конкретные причины внутри.

Пример:

**Производственный план нужно обновить**

Причины:
- изменились параметры техкарты;
- не заполнены даты.

Button:
`Проверить план`

---

## 5. Приоритет сообщения

В каждой карточке показывать в таком порядке:

1. Человеческий заголовок.
2. Что конкретно не заполнено.
3. Где это находится.
4. Что сделать.
5. Action button.

Технический diagnostic code не показывать обычному менеджеру.

Debug Mode может продолжать показывать code/id отдельно.

---

## 6. Короткие тексты

Не повторять одинаковую фразу:
`Без норм техкарту нельзя корректно рассчитать и запланировать`
в каждой карточке.

Если несколько ошибок относятся к одной категории, писать общий смысл один раз.

Modal должен быть короче текущего.

---

## 7. Источник истины

Не менять backend readiness rules.

Использовать:
- backend diagnostic code;
- entity/operation name;
- fix_action;
- fix_url;
- severity.

Если backend не отдаёт operation name:
- использовать уже доступный snapshot/operation label из read model;
- если его нет — зафиксировать `BACKEND GAP`.

Не хардкодить имена операций по id.

---

## 8. Browser acceptance

Проверить кейс, аналогичный текущему скриншоту:

Ожидаемый modal должен выглядеть примерно так:

### Техкарта требует настройки

**Нужно заполнить параметры сборки**
Сборка: `Пошив футболки`
Не заполнено: `Норма пошива`
[Открыть сборку]

**Нужно заполнить нормы расхода**
Не заполнено для операций:
- Сублимационная печать
- Термоперенос
[Заполнить нормы]

**Укажите даты производства и отгрузки**
[Указать даты]

**Производственный план нужно пересчитать**
[Пересчитать план]

То есть вместо 6–7 повторяющихся карточек должно остаться 3–4 понятных действия.

---

## 9. Tests

Минимум:
- friendly copy mapping;
- operation name included;
- same diagnostic code grouped;
- duplicate plan diagnostics grouped;
- different fix actions not grouped;
- warning/blocking severity preserved;
- Debug technical code remains available only in Debug context;
- buttons navigate correctly.

Проверки:
- targeted frontend tests;
- eslint;
- tsc;
- production build;
- `python scripts/check_project.py`;
- git diff --check.

---

## Не делать
- backend business rule changes;
- readiness semantics changes;
- production core changes;
- Scheduler/Kanban/Queue/Calendar changes;
- commit/push.

---

## Acceptance

Готово, если менеджер по каждому сообщению сразу понимает:

1. что не заполнено;
2. для какой операции/сборки;
3. где это исправить;
4. какое действие выполнить;

и одинаковые diagnostics больше не создают визуальные дубли.

Финальная строка:

`PC-06.0F FRIENDLY PREFLIGHT COPY AND DEDUP READY`

## Результат

Окно остаётся представлением GET readiness и уже посчитанных норм модели. На техкарте 1310-1 (id 6) запуск показывает четыре карточки: параметры сборки («норма пошива»), даты, нормы расхода для «Сублимационная печать» и «Термоперенос», один пересчёт плана с тремя причинами. Сборка на этой карточке пустая («—»), поэтому имя сборки в текст не подставляется. Коды диагностики в окне не показываются.
