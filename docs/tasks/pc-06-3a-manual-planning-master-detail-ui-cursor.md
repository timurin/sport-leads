# PC-06.3A — Manual Planning Master-Detail UI

## Исполнитель
Cursor

## Цель
Переделать `/production/calendar/manual-planning` из списка повторяющихся assignments в понятный интерфейс:

`одна ТК → её маршрут → перенос конкретной будущей операции`

Backend planning semantics не менять. Переиспользовать существующие preview/apply contracts.

## Проблема текущего UI
Сейчас одна ТК отображается много раз — по каждому участку/assignment. Для менеджера это выглядит как дубли и неясно, что именно планируется.

## Новый UX

### Левая колонка — ТК, каждая один раз
Показывать:
- № ТК / заказ;
- модель;
- количество;
- текущий участок;
- дата отгрузки;
- ETA;
- риск;
- прогресс маршрута, например `2 из 7 завершено`.

Фильтры:
- поиск;
- участок;
- риск;
- дата отгрузки;
- `Только требующие перепланирования`.

Не показывать одну ТК несколько раз.

### Правая колонка — план выбранной ТК
После выбора ТК показать маршрут:

`Дизайн ✓ → Сублимация ● → Термоперенос ○ → Раскрой ○ → Пошив ○ → ВТО ○ → Упаковка ○`

Ниже таблица:

`Операция | Участок | План | Состояние`

Состояния:
- completed — locked;
- in_progress — locked;
- waiting/future — editable.

Редактировать можно только future operations.

## Перенос операции
При выборе future operation открыть компактный редактор:
- операция;
- участок;
- текущая дата;
- новая дата;
- при наличии — доступность/загрузка участка на выбранный день.

Кнопки:
- `Отмена`
- `Предпросмотр`
- `Применить перенос`

## Preview
Перед apply показать server preview:
- старая → новая дата;
- какие downstream operations сдвинутся;
- новая ETA;
- дата отгрузки;
- запас/риск;
- warnings/blockers.

Не считать downstream на frontend.

## Режим переноса
Если backend contract уже поддерживает оба варианта, показать:
- `Только эту операцию`
- `Эту и последующие`

Если backend этого не поддерживает — НЕ придумывать frontend-семантику; показать только существующий supported flow и отметить BACKEND GAP.

## Мощности
Не делать второй большой календарь.

Допустимо показать компактный availability strip для выбранного участка на 7–14 дней, только если эти данные уже доступны:
- дата;
- load %;
- выходной/нет мощности.

Если API нет — не расширять scope.

## Инварианты
- completed/in_progress нельзя переносить;
- future assignment не меняет Kanban/current_workshop;
- apply идёт только через backend;
- stale preview/revision должен блокировать apply;
- deleted TK не показывать;
- completed TK не показывать как editable;
- production fact не менять.

## Технически
Переиспользовать существующие:
- manual planning API;
- preview/apply;
- planning revision/fingerprint;
- persisted ETA;
- CalendarAssignment read model.

Не делать новый Scheduler.

## Адаптивность
Desktop:
- master-detail 35/65 или близко;
- обе колонки без лишней высоты.

Tablet:
- 40/60 или stacked при нехватке.

Mobile:
- сначала список ТК;
- после выбора открывается detail screen/panel;
- без горизонтального скролла всей страницы.

## Визуальный стиль
Использовать текущий SPORT-LEADS UI context.
Без тяжёлых карточек и лишних рамок.
Главное — читаемость маршрута и понятный перенос операции.

## Проверка
Использовать safe test TK из разрешённых SKU.

Проверить:
1. одна ТК = одна строка слева;
2. маршрут отображается целиком;
3. completed/in_progress locked;
4. future operation editable;
5. preview показывает последствия;
6. apply меняет только план;
7. Kanban/Queue/fact не меняются;
8. stale preview блокирует apply;
9. deleted TK отсутствует;
10. mobile/desktop визуально корректны.

## Не делать
- Scheduler refactor;
- Capacity redesign;
- Calendar redesign;
- Queue/Kanban changes;
- production facts;
- commit/push.

## Acceptance
Готово, если менеджер может:
1. выбрать ТК один раз;
2. увидеть её маршрут;
3. выбрать будущую операцию;
4. понять последствия переноса;
5. применить изменение без риска затронуть факт.
