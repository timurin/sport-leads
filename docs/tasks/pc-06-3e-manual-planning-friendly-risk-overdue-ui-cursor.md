# PC-06.3E — Manual Planning Friendly Risk / Overdue UI

## Исполнитель
Cursor

## Цель
Сделать экран ручного планирования визуально понятным менеджеру:
- сразу видно, какая ТК просрочена;
- видно, какая именно операция просрочена;
- понятно, почему карта требует перепланирования;
- фильтры читаются человеческим языком;
- интерфейс остаётся master-detail: одна ТК слева, маршрут справа.

Backend planning semantics не менять.

## 1. Проблема текущего UI
Сейчас:
- чекбокс `Только требующие перепланирования` не объясняет причину;
- просрочка конкретной операции не видна в списке;
- пустое состояние `Нет техкарт с открытым планом` не соответствует смыслу выбранного фильтра;
- список выглядит технически, а не как рабочий инструмент менеджера.

## 2. Новый визуальный принцип
Левая колонка должна отвечать на вопрос:
`Какие ТК требуют моего внимания и почему?`

Каждая ТК — один компактный friendly-card.

Показывать:
- № ТК / заказ;
- модель;
- quantity;
- текущий участок;
- дата отгрузки;
- ETA;
- краткий прогресс маршрута;
- problem/status badge.

## 3. Problem badges
Использовать server-derived/read-model данные, не считать бизнес-риски заново на frontend.

### overdue
Красный:
`Просрочена на N дн.`

Дополнительная строка:
`ВТО · план 14.10.2026`

Если несколько:
`Просрочено операций: 2`
и показать самую раннюю/критичную.

### risk
Оранжевый:
`Риск срока`

Показать:
`ETA 31.10 · Отгрузка 30.10`

### stale / replan required
Жёлтый:
`Требует перепланирования`

### normal
Нейтральный/позитивный:
`План актуален`

Не перегружать карточку несколькими одинаковыми сообщениями.

## 4. Фильтры
Заменить checkbox `Только требующие перепланирования` на понятный control:

`Состояние плана`

Варианты:
- Все
- Просроченные
- В риске
- Требуют перепланирования
- Без проблем

Дополнительно сохранить:
- Поиск
- Участок
- Дата отгрузки

Если backend contract различает несколько состояний одновременно, не терять это; фильтр должен использовать canonical server flags/statuses.

## 5. Empty states
Текст зависит от выбранного фильтра.

### Все
`Нет техкарт для ручного планирования.`

### Просроченные
`Просроченных операций не найдено.`

### В риске
`Техкарт с риском срока нет.`

### Требуют перепланирования
`Нет техкарт, требующих перепланирования.`

### Без проблем
`Нет техкарт с актуальным планом.`

Не использовать универсальное `Нет техкарт с открытым планом`, если выбран конкретный фильтр.

## 6. Правая колонка
Сохранить текущий маршрут и replan flow PC-06.3A/3C.

После выбора ТК сверху показать friendly summary:
- текущий статус плана;
- ETA;
- дата отгрузки;
- запас;
- количество просроченных операций;
- ближайшая проблема.

Пример:
`Просрочено 2 операции`
`Самая ранняя: ВТО · 14.10.2026`
`ETA: 30.10`
`Отгрузка: 31.10`
`Запас: 1 день`

Ниже — маршрут.

## 7. Route highlighting
В таблице маршрута:
- overdue pending operation — красный badge `Просрочена`;
- future pending — `Запланирована`;
- in_progress — `В работе`;
- completed — `Завершена`;
- stale/replan-required — warning marker, если backend это отдаёт.

Не использовать цвет workshop как замену operation state.

## 8. Backend gap policy
Если текущий read model не отдаёт достаточные поля для:
- overdue count;
- earliest overdue operation;
- risk;
- stale/replan_required;

не считать это сложной логикой на frontend.

В этом случае:
- использовать только уже доступные canonical поля;
- зафиксировать точный `BACKEND GAP`;
- не строить второй risk engine в UI.

Допустим простой presentation helper для formatting/counting уже полученных flags, но не бизнес-расчёт.

## 9. Mobile
На 390px:
- фильтры в 1–2 строки;
- cards в одну колонку;
- badge не ломает ширину;
- после выбора ТК detail открывается отдельно;
- `К списку техкарт` остаётся;
- без горизонтального scroll страницы.

## 10. Browser checks
Проверить минимум:
1. overdue card;
2. risk card;
3. normal card;
4. replan-required/stale card, если есть;
5. empty state для каждого фильтра;
6. desktop;
7. 390px mobile.

Не менять production facts.

## Acceptance
Готово, если менеджер без открытия карточки понимает:
1. какая ТК просрочена;
2. какая операция просрочена;
3. сколько дней просрочки;
4. есть ли риск срока;
5. требует ли карта перепланирования;
6. почему список пуст при выбранном фильтре.

Финальная строка:
`PC-06.3E MANUAL PLANNING FRIENDLY RISK UI READY`

## Результат

BACKEND GAP, список и доска:

- нет признака просрочки операции;
- нет числа дней просрочки;
- нет самой ранней просроченной операции;
- нет list-level ETA, `on_time`, `delay_days`, `buffer_days`, `replan_required`.

Эти поля есть только в detail `planning_summary` (ETA, отгрузка, запас, `on_time`, `replan_required`). Доска отдаёт `planning_state`: `stale`/`invalid` → «Требует перепланирования». Экран не вычитает `planned_date`. Фильтры «Просроченные» и «В риске» поэтому не подменяют пустой результат фразой «не найдено».
