# PC-06.3G — Manual Planning UI Redesign

## Исполнитель
Cursor

## Цель
Переделать интерфейс `/production/calendar/planning` так, чтобы он был понятен менеджеру без знания внутренней структуры assignments/snapshot.

Текущий экран формально master-detail, но визуально остаётся похож на технический список и не даёт быстрого ответа:
- что требует внимания;
- что просрочено;
- что можно перенести;
- что произойдёт после переноса.

Нужен именно UX-redesign, не очередной косметический patch.

## Главный сценарий
Менеджер открывает экран и за 5–10 секунд должен понять:
1. какие ТК требуют внимания;
2. почему;
3. какую операцию можно перенести;
4. что изменится после переноса;
5. можно ли безопасно применить изменение.

## 1. Новая компоновка

### Верхняя панель
Оставить только:
- Поиск;
- Состояние плана;
- Участок;
- Дата отгрузки;
- компактные счётчики:
  - Просрочено;
  - В риске;
  - Требуют перепланирования.

Убрать визуальный шум и лишние большие пустые зоны.

### Левая часть — список ТК
Не таблица и не плоские строки.
Сделать компактные карточки 1 ТК = 1 card.

В карточке:
- № ТК крупнее;
- заказ/клиент вторично;
- модель + количество;
- текущий участок;
- прогресс маршрута `4 из 7`;
- ETA / отгрузка;
- один главный badge состояния;
- если есть проблема — одна понятная строка причины.

Пример:

`STAB-P1-001-1`
`Футболка 201.2 · 4 шт.`
`Пошив · 4 из 7`
`ETA 30.10 · Отгрузка 31.10`
`🔴 Просрочена на 2 дня`
`ВТО · план 14.10`

Карточка целиком кликабельна.

## 2. Приоритет состояний
Если backend отдаёт несколько признаков, визуальный приоритет:
1. overdue
2. risk
3. replan_required/stale
4. healthy

Не показывать 3–4 badges одновременно.

## 3. Правая часть — выбранная ТК
Верхний summary:
- ТК;
- модель;
- quantity;
- текущий участок;
- ETA;
- отгрузка;
- запас;
- главный problem badge.

Ниже — горизонтальный roadmap маршрута с компактными step-chips:
`Дизайн ✓ → Печать ✓ → Раскрой ● → Пошив ○ → ВТО ○ → Упаковка ○`

После roadmap — таблица/список операций.

## 4. Операции маршрута
Для каждой операции:
- название;
- участок;
- плановая дата;
- статус;
- action справа.

Statuses:
- Завершена — locked;
- В работе — locked;
- Просрочена — красный акцент;
- Запланирована — нейтральный;
- Требует перепланирования — amber.

Action только у editable pending:
`Перенести`

Не показывать action у protected operations.

## 5. Редактор переноса
После клика `Перенести` не растягивать всю страницу.
Открывать справа/внутри detail компактную панель:

- Операция;
- Текущая дата;
- Новая дата;
- Режим:
  - Только эту операцию
  - Эту и последующие
- `Предпросмотр`

После preview показывать отдельный блок `Что изменится`:
- выбранная операция old → new;
- downstream changes;
- ETA old → new;
- запас old → new;
- риск;
- blockers/warnings.

Primary button:
`Применить перенос`

Secondary:
`Отмена`

## 6. Пустые состояния
Не оставлять большую пустую правую колонку с одной строкой `Выберите техкарту`.

Если ТК не выбрана, показать компактный friendly placeholder:
`Выберите техкарту слева, чтобы увидеть маршрут и изменить будущие операции.`

Если фильтр ничего не нашёл — контекстный empty state по выбранному фильтру.

## 7. Desktop layout
Цель: рабочий экран, а не форма.

Рекомендуемая структура:
- left list: ~32–36%;
- right detail: ~64–68%;
- sticky filters сверху;
- список слева со своим scroll;
- detail справа со своим scroll только при необходимости.

Не делать огромную пустую область.

## 8. Mobile
390 px:
- сначала список ТК;
- выбор открывает detail на весь экран;
- `← К списку`;
- roadmap переносится в несколько строк;
- редактор переноса в одну колонку;
- sticky bottom actions допустимы для `Предпросмотр / Применить`.

## 9. Backend gap
Если PC-06.3F ещё не готов и backend не отдаёт overdue/risk fields:
- не придумывать расчёты;
- использовать доступные поля;
- пометить конкретные места как `BACKEND GAP`;
- визуальный redesign всё равно выполнить.

После PC-06.3F просто подключить новые поля без ещё одного redesign.

## 10. Что не менять
- Scheduler;
- preview/apply API;
- replan semantics;
- Kanban/Queue;
- Calendar;
- production facts;
- backend models;
- commit/push.

## 11. Browser acceptance
Показать скриншоты минимум:
- desktop 1440;
- laptop 1280;
- mobile 390;
- ТК без проблем;
- ТК с проблемой;
- открытый editor;
- preview результата.

## Acceptance
Готово, если менеджер без объяснений понимает:
- какая ТК проблемная;
- почему;
- где она сейчас;
- что можно перенести;
- что изменится после переноса.

Финальная строка:
`PC-06.3G MANUAL PLANNING UX REDESIGN READY`
