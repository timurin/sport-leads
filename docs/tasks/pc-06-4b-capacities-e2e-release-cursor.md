# PC-06.4B — Capacities E2E + release (Cursor)

## Цель
Закрыть PC-06.4A проверкой живого сохранения и безопасным выпуском в production. Работать с текущим состоянием рабочей ветки; без рефакторинга Capacity/Demand/Scheduler.

## Источники
`docs/architecture/SL-PROJECT-MEMORY-v1.md` (PM-CAPACITY, PM-OPS), `docs/architecture/SL-UI-CONTEXT-v1.md` (UI-CALENDAR), `docs/architecture/production-calendar-shared-capacity-pc-03-7a.md`, `docs/architecture/work-center-capacity-pc-04-4d.md`, соответствующие разделы `SL-DATA-FLOW-v1.md`. Сначала проверить git status и существующий diff PC-06.4A.

## Проверить
1. С авторизованной сессией открыть `/production/calendar/capacity` на локальных 3001/8000. На существующем **тестовом** нестаночном ресурсе изменить параметр графика и вернуть исходное значение после проверки; проверить сохранение, перезагрузку, чтение API и отсутствие изменений соседних ресурсов. Исключение даты создать/прочитать/удалить **только на тестовом ресурсе**; не трогать реальные данные, если подходящего тестового ресурса нет — сообщить `BLOCKED` и дать шаги ручной проверки.
2. Для реально привязанного WorkCenter сверить доступно/занято/остаток/% на выбранную дату с `GET /work-centers/{id}/capacity/load`; проверить нерабочий день, отсутствующий адаптер, API error/retry, отдельно «Неизвестно» для персонала/бригады и «Без расчёта» для milestone. Не использовать `POST /capacity/load-state` как источник сохранённой загрузки.
3. Проверить лейблы «Сегодня/Неделя»: если «Неделя» означает выбор дня, текст UI обязан это точно объяснять; не выдавать просмотр одной даты за суммарный недельный отчёт. Без новых endpoint.
4. Responsive 1440/1024/768/390/320; модальное/раскрытая строка, длинные названия, отсутствие горизонтального скролла страницы и ошибок JS. Проверить изменение даты и исключений, ошибки записи, перезагрузку.
5. Targeted tests, затем `python scripts/check_project.py` (10/10), generator/twin check и `git diff --check`.

## Границы
Точечно исправлять лишь подтверждённые P0/P1 баги PC-06.4A. Не создавать расход/занятость персонала без persisted allocations и отдельного API-контракта. Не добавлять batch endpoint и не менять Scheduler, DB, тестовые/боевые записи. Не запускать cleanup/reset.

## Выпуск
После зелёных проверок и разрешённых регрессионных исправлений: commit завершённого PC-06.4A/B + relevant docs/tasks → push `main` → подтвердить GitHub Action `deploy-production.yml` → authenticated smoke `/production/calendar/capacity` на `https://sport-lead.ru` (не считать только HTTP200 login доказательством работы UI), отдельно зафиксировать отсутствие права на production-write, если не разрешено. При неготовности E2E **не объявлять deployed**; выдать точный blocker и оставить изменения для последующей приёмки.

Commit, run/deploy, проверки и ширины, точные E2E сценарии и восстановление тестовых данных, проблемы/ограничения, статус `PC-06.4A/B`. Обновить roadmap/ERP-check/project structure/UI context/data-flow и HTML twins **только если статус или контракт реально изменились**.
