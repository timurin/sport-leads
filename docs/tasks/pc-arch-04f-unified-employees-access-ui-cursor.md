## Цель
Убрать два независимых рабочих интерфейса `/settings/users` и `/settings/organizations/employees/[id]` в пользу **одного раздела сотрудников и доступа**. Не сливать сущности Employee/PlatformUser в БД.

## Объём
1. Основной вход `/settings/employees`: сотрудники, поиск/фильтры, доступность и статус учётной записи. Единая карточка `/settings/employees/[id]` с вкладками **Основное** и **Доступ к платформе**. Сохранить организационную принадлежность, кадровые атрибуты и уже существующие сценарии сотрудников.
2. Вкладка доступа: привязанная учётная запись (или отсутствие), операции link/unlink с подтверждением и защитой от ошибок, список назначенных **групп** и читаемый список **эффективных разрешений**. Кадровая категория/должность не заменяет RBAC-группы.
3. Администратор (проверять реальное разрешение из API, не сравнивать имя роли) управляет назначениями групп через модальное окно. Поддержать **несколько групп** одному пользователю, effective union, preview → подтверждение → apply, конфликты версий / 403 / 404 / 409 / сеть. Не имитировать успешное сохранение.
4. Управление самими группами и матрицей разрешений — **модальное окно** в едином разделе, по API ARCH-04E. Реальные permissions каталога, защита системных групп и последнего администратора; изменения матрицы только при достаточных правах. Без собственной параллельной модели RBAC на клиенте.
5. **NAV-04 только в пределах ARCH-04**: из списка сотрудник открывается модально, из карточки настройки прав — следующим уровнем; закрытие верхнего уровня возвращает к предыдущему модальному окну, затем к списку. Сохранять фильтры, вкладку, scroll, черновики по согласованной политике; Back/Forward, Escape, focus trap/restore, защита несохранённых изменений. Прямые глубокие ссылки должны работать при загрузке без фоновой страницы. Мобильная адаптация 1440/768/390/320.
6. Старые ссылки `/settings/users` и `/settings/organizations/employees/[id]` корректно ведут в новый раздел/карточку (с учётом deep links и возврата), но не оставляют второй независимый экран редактирования. Учесть прежние ссылки из навигации/других модулей.

## Безопасность и ограничения
- Frontend использует существующие backend API ARCH-04A/04E. Не менять миграции, парольную логику, RBAC backend, производственную историю.
- Не делать массовую автоматическую привязку Employee ↔ PlatformUser; не менять права admin и реальных сотрудников для теста.
- Любые ошибки разрешений — безопасный отказ, с сохранением текущих значений на форме; состояния loading/empty/error обязательно.
- Если API не покрывает целевой UX, зафиксировать точный пробел; не придумывать обход через опасное действие.
- Не объявлять NAV-04 глобальным стандартом до подтверждённой приёмки.
