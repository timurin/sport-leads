## Цель
Проверить целостный сценарий «сотрудник → учётная запись → несколько групп → effective permissions», NAV-04 и безопасно выпустить связанные изменения одним релизом. Не расширять scope и не менять действующие права пользователей ради E2E.

## Проверки до выпуска
1. Проверить diff/status и состав релиза; не включать посторонний WIP. Сверить актуальную миграционную цепочку ARCH-04A/04E, upgrade/downgrade на отдельной тестовой PostgreSQL БД. Не выполнять destructive downgrade на рабочей БД.
2. В локальной тестовой БД создать выделенные E2E employee + platform user + две НЕсистемные тестовые группы; записать IDs. Проверить через UI и GET: привязка, множественное назначение, effective union, preview → apply, изменение матрицы одной тестовой группы, сохранение после reload и разрыв связи с подтверждением. Проверить, что роли/права `admin` и `lm@mosmade.ru` не менялись. Удалить только созданные E2E fixtures, если безопасно и история/ограничения допускают; иначе перечислить оставшиеся IDs.
3. Негативные сценарии: 403 (серверная проверка), 409 с сохранением черновика, защита системной группы и последнего администратора; запрет админских действий через прямой API без полномочия. Тесты не заменяют полноценную браузерную проверку основного happy path.
4. NAV-04: список → модальная карточка → вложенное окно групп/матрицы → Escape назад на карточку → закрытие к исходному списку. Проверить Back/Forward, прямую ссылку (полноэкранное представление), focus return, предупреждение о несохранённых изменениях, 1440/768/390/320, отсутствие горизонтального overflow. Проверить старые маршруты, включая `/settings/users?user=1`, без подмены ID аккаунта ID сотрудника.
5. Проверить наличие учёток без сотрудника: доступ к их управлению из **единого** раздела сохраняется. Редактирование Employee не должно изменять реквизиты PlatformUser, а кадровая категория/должность не должны выдавать RBAC права.
6. `python scripts/check_project.py` 10/10, `git diff --check`, релевантные интеграционные тесты. Проверить документы, требуемые существующими контрактами, без бессмысленных правок.

## Выпуск и критерии готовности
- При любом провале миграции, API/security или E2E: **STOP**, без commit/push/deploy; предоставить точный блокер.
- Если всё PASS: один целевой commit только завершённых ARCH-04 изменений → push `main` → проверить GitHub Actions и SHA production. Убедиться, что продовая миграция завершилась без ошибок.
- Production QA **без мутации рабочих данных и прав**: единый список, карточка, вкладка доступа, чтение групп и эффективных прав, старые ссылки, direct link, NAV-04, desktop/mobile. Не применять матрицу/назначение к реальным учеткам. Если нет безопасной записи — честно отметить prod write E2E как непроверенный.
- Отчёт: SHA, workflow, состав релиза, результаты DB/API/UI/NAV-04/permissions, данные и cleanup тестовых записей, остаточные риски. **NAV-04 не объявлять глобальным правилом**: это отдельное решение после оценки итогового E2E.
