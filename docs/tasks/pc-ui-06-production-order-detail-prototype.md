# PC-UI-06 — UI-C: Карточка производственного заказа (дизайн-прототип)

## Контекст
- Production Calendar v0.1; PC-01 и PC-02 завершены, PC-02.1 остаётся открытым по архитектурным блокерам.
- UI-A (недельное табло) — базовый прототип, UI-B (быстрое добавление заказа после PC-UI-05.1) **утверждён владельцем**. Это утверждение относится только к UI-B; общий `DESIGN-APPROVED` **не устанавливать**.
- Перед выполнением прочитать `AGENTS.md`, актуальные `docs/roadmap/production-calendar-v0.1.md`, `docs/roadmap/roadmap-v1.1.md`, `docs/architecture/production-calendar-pc-02.md`, `docs/tasks/production-calendar-pc-02-1-validation.md` (если существует), а также `docs/design/production-calendar/{ui-contract.md,navigation.md,screens/create-order.md}`. Использовать реальные пути, если документация размещена иначе.
- Эталон оформления — существующая дизайн-система SPORT UNIFORM, `SL-UI-BASE-v1`, актуальные прототипы `weekly-board-prototype.html` и `create-order-prototype.html`, визуальные контракты DS-SHELL-01/02. Оболочку приложения не изменять.

## Цель
Создать **автономный интерактивный single-file HTML** экрана UI-C «Производственный заказ» для визуального согласования владельцем. Только демоданные; никакой записи в приложение и новых API.

## Микротаски

### PC-UI-06.1 — Состав карточки и сценарии
1. Создать краткую спецификацию `docs/design/production-calendar/screens/production-order.md`: структура карточки, состояния, переходы из UI-A и UI-B, desktop/mobile.
2. Уточнить названия: заказ календаря связывается с **существующей standalone-группой ТК**, выбранной ТК, моделью, вариантом сборки и маршрутом; не изображать его отдельным заказом покупателя из CRM.
3. Продумать read-only снимок исходных данных и независимые плановые поля календаря; изменения календарных статусов **не меняют факт и маршрут ТК**.

### PC-UI-06.2 — Шапка и информация о заказе
1. Заголовок «Производственный заказ» + ручной номер существующей группы ТК (демоданные), хлебные крошки и возврат в календарь.
2. Информационные поля: № группы, № ТК, изделие, модель, вариант сборки, количество, маршрут ТК, плановая дата готовности и статус календаря.
3. Указать происхождение данных (снимок ТК / ручное поле календаря) без перегруза интерфейса.
4. Действия — «К календарю», «Редактировать план» (только демонстрационный сценарий), меню без ложного сохранения.

### PC-UI-06.3 — Маршрут и зависимости
1. Показать **две параллельные ветви календаря**: «Закупка материалов» и «Дизайн». «Печать» разрешается после завершения обеих; далее «Раскрой → Пошив → Упаковка» последовательно.
2. Не создавать впечатление, будто изменён линейный маршрут существующей ТК: подписать схему «Зависимости календаря»; рядом при необходимости отдельно показать название маршрута ТК.
3. Различить состояния: не запланировано, запланировано, готово к запуску, в работе, приостановлено, завершено, заблокировано. Последнее — **признак невозможности запуска**, не подмена основного статуса.
4. Показать в демоданных сценарии: закупка завершена / дизайн в работе (печать заблокирована); обе ветви завершены (печать доступна); просрочка предыдущей операции. Переключатель сценариев — только для демонстрации.

### PC-UI-06.4 — Таблица операций и нагрузка
1. Строки: участок/операция, календарный статус, блокировка и её причина, план начала/окончания, факт (отдельно от факта ТК), запланированное количество, трудоёмкость, ответственный (только если подтверждён доступный тип данных), действия.
2. Для пошива показывать трудоёмкость из **снимка выбранного варианта сборки**: сумма применимых `duration_seconds × кратность × количество` с переводом секунд в часы. Не выдумывать нормативы закупки или производственных участков.
3. При отсутствии подтверждённой нормы отображать «Нагрузка не рассчитана», а не 0 ч или 0%; учесть нулевую мощность и перегрузку.
4. План и фактические отметки не должны автоматически переходить в существующие статусы ТК.

### PC-UI-06.5 — Сводка и UX-состояния
1. Компактная сводка: завершённые операции (например, `2/6`, **не** утверждение о проценте физических изделий), рассчитанные часы известных операций, ожидающие/заблокированные операции, дата готовности и риск срока.
2. Отдельно отображать перегрузку мощности и зависимость/блокировку запуска.
3. Подробности этапа показывать во всплывающем окне/панели без изменения данных; предупредить о демонстрационном режиме.
4. Обработать пустые данные, длинные номера/наименования, отсутствие маршрута или нормы и отсутствие плановых дат.

### PC-UI-06.6 — Адаптивность, доступность, проверки
1. Создать `docs/design/production-calendar/production-order-prototype.html` — автономный HTML со встроенными CSS и JS, без внешних зависимостей.
2. Desktop/laptop: плотная, читаемая карточка с маршрутом и таблицей; tablet/mobile: адаптивные карточки операций без горизонтальной прокрутки страницы.
3. Не допускать вложенной прокрутки в обычных desktop-сценариях; при неизбежном переполнении на малом экране допускается один понятный вертикальный скролл.
4. Проверить 1440×900, 1366×768, 1280×800, 1024×768, 768×1024, 390×844, 320×568; если браузер недоступен — честно указать непроверенные параметры, не заявлять визуальный тест.
5. Проверить табуляцию, Escape, возврат фокуса после диалогов, смену сценариев, статусы, формулы, отсутствие консольных ошибок (при доступном браузере).
6. Обновить `ui-contract.md`, `navigation.md`, экранную спецификацию и статусы Markdown/HTML roadmap **только по факту выполнения**. Если действующий генератор HTML предусмотрен — использовать его; не вести вручную независимые статусы.
