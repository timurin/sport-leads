# PC-UI-08 — UI-E: ручное распределение операций по датам

## Контекст
UI-A (недельное табло), UI-B (создание), UI-C (карточка), UI-D («участок — день») имеют автономные прототипы. PC-UI-07.1 исправила навигацию UI-A → UI-D → UI-C → UI-D → UI-A. UI-B и UI-C приняты владельцем; UI-D технически подготовлен, но **OWNER-APPROVED пока не подтверждён владельцем**. Общий DESIGN-APPROVED не ставить.

Используй актуальные `AGENTS.md`, `docs/design/production-calendar/{ui-contract.md,navigation.md}`, спецификации экранов и `docs/architecture/production-calendar-pc-02.md`; сохраняй стиль SL-UI-BASE-v1 / SPORT UNIFORM и DS-SHELL-01/02. При расхождении текстовых требований с актуальным контрактом явно сообщи о конфликте, а не меняй архитектуру молча.

## Цель
Спроектировать самостоятельный **single-file HTML/CSS/JS** прототип `docs/design/production-calendar/manual-scheduling-prototype.html` — диспетчер вручную назначает или переносит операции календарного заказа на даты и видит последствия для загрузки. Только локальное demo-state, без API и сохранения в приложении.

## UI и действия
1. Контекст: номер производственного заказа/группы ТК, изделие, модель, количество, срок; ссылка назад к UI-C или UI-D с сохранением допустимых локальных `date`, `stage`, `week`, `return` параметров (не создавать open redirect).
2. Слева (или сверху на узких экранах): операции заказа и их статусы, включая **нераспределённые**. Закупка и дизайн — параллельные предшественники печати; далее печать → раскрой → пошив → упаковка. Показывать зависимости, не переписывая исходный линейный маршрут ТК.
3. Основная рабочая область: наглядное ручное назначение даты выбранной операции и её **планового количества**; возможность изменить дату, снять назначение и распределить количество по нескольким датам (сумма не больше объёма операции/заказа). Можно реализовать доступными контролами и кнопками; drag-and-drop необязателен, клавиатурный сценарий обязателен.
4. Для выбранного участка/даты показать **было → станет**: известный план в человеко-часах, доступная мощность и загрузка %. Пошив — snapshot `sum(duration_seconds × multiplicity)` на изделие × количество; не пересчитывать и не изменять исходную ТК/модель. Другие участки — только явно помеченные ручные демооценки, не выдуманные нормы; закупка — ручное подтверждение готовности, без часов.
5. Разные сигналы: перегрузка >100%, 80–100%, недостающая норма, 0 мощности, выходной, блокировка **фактического запуска** предшественниками. Разрешить **планировать** зависимую операцию до завершения предыдущей, но не обозначать её как допущенную к запуску. Реальный запуск и разрешения — только будущий сервер.
6. На экране есть отмена локального изменения, сброс демосценария, демонстрационное «Применить план» с ясным сообщением **«изменения не сохранены»**; никакой имитации сохранения в backend. Покажи конфликт и причину; решение перегрузки диспетчер принимает вручную, автоматического перепланирования нет.
7. Адаптивность desktop 1440/1366/1280, tablet 1024/768, mobile 390/320; без горизонтального переполнения всей страницы, видимые действия, разумная компоновка без вложенных scroll-ловушек.

## Демосценарии
- Нераспределённая операция → назначение.
- Перенос с одного рабочего дня на другой с обновлением обеих загрузок.
- Разделение 100 изделий на два дня (например 40 + 60), запрет превышения общего количества.
- Превышение мощности / допустимый резерв.
- Отсутствие нормы (не заменять 0), нулевая мощность, выходной.
- Печать запланирована при незавершённом дизайне: **план допустим, запуск блокирован**.
- Отмена/сброс; переходы обратно с сохранением контекста.
