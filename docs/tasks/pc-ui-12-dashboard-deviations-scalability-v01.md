# PC-UI-12 — Dashboard календаря + Центр отклонений (масштабирование 100 заказов)

## Контекст
Sport-Leads, Production Calendar v0.1. Владелец утвердил UI-A–UI-F. UI-G/H остаются `READY FOR OWNER REVIEW`; общий `DESIGN-APPROVED` не выставлять. Последние реализации: `docs/design/production-calendar/gantt-prototype.html`, `risks-conflicts-prototype.html`; PC-UI-10/11.1 закрепил логику маршрутов и конфликтов. Прочитать `AGENTS.md`, канонические roadmap, UI-contract, capacity contract, спецификации экранов и DS-SHELL-01/02 перед изменениями. Не менять утверждённые экраны и оболочку.

## Решение владельца
- **UI-A** — основной недельный календарь для оперативного планирования.
- **UI-G** — **«Дашборд производственного календаря»**, не второй календарь/многострочный Гант по всем операциям.
- **UI-H** — **«Центр отклонений»**, не длинный журнал карточек по одному сигналу.
- Детальный Гант имеет смысл **только для одного заказа** (концептуально в UI-C); утверждённый UI-C не изменять, пока владелец не проверит новую компоновку. При необходимости сделать отдельный автономный `order-gantt-prototype.html` как демонстрационный drill-down и зафиксировать будущую точку интеграции.

## Работа
1. Переработать автономный UI-G (сохранить путь файла для ссылок): KPI по текущему периоду, наглядные графики *плановая нагрузка vs доступная мощность* по каждому участку, динамика по дням/неделям, свободная мощность, узкие места, фильтры периода/участка и drill-down «участок → дата → ресурсы/назначения» с переходом к UI-A/UI-D/UI-E/UI-F. Не показывать отдельную строку каждой операции во всех заказах по умолчанию. В «печати» четыре плоттера, каландр, операторы раздельно; «раскрой» — общий пул двух раскройщиков, лазер и отдельный оператор; «упаковка» — одна бригада двух человек (800 шт./10 ч). Не складывать машинные и человеко-часы в общую процентную загрузку. Неизвестные нормы = «недостаточно данных», не 0% и не фиктивный резерв.
2. Переработать UI-H: компактные агрегированные **группы причин** (перегрузка ресурса/даты, недоступность, материалы, нарушение зависимостей, срок, неизвестные нормы). Сверху KPI по уникальным затронутым заказам и по сигналам с явными подписями; для каждой группы — количество случаев/заказов, период, серьезность, возможность раскрытия; внутри — компактная таблица с поиском по номеру, фильтрами (период, участок, тип, критичность), сортировкой, пагинацией или виртуализацией, панелью деталей и проверяемым локальным действием. **Один общий конфликт оборудования с N затронутыми заказами — один групповой конфликт, не N идентичных карточек**; при этом события не теряются. Разделить `hard`/`risk`/`unknown`. Не скрывать факты конфликтов вследствие фильтрации или объединения.
3. Подготовить реалистичные **только синтетические** сценарии на 5, 30, 50, 100 заказов. Проверить удобство высоты страниц и производительность интерактивности: главное представление не растёт линейно как «заказы × операции», а детализация загружается/раскрывается по запросу. Данные только в памяти страницы, локальные сценарии сбрасываемы. При масштабировании учитывать отдельные партийные назначения, фактические правила очередности, даты и мощности из контрактов. Не создавать иллюзию реальной ERP-интеграции.
4. Если создаётся прототип Ганта отдельного заказа, показать только один заказ, последовательность/параллельность закупки и дизайна, подготовку, плоттеры → каландр → раскрой → пошив → упаковку, частичные партии и отдельную блокировку запуска при незавершённых предшественниках. Ссылка из UI-G допустима, UI-C неизменен.
5. Обновить спецификации UI-G/H, `ui-contract.md`, roadmap MD и генерируемый HTML twin в соответствии с действующим механизмом синхронизации. Сохранить прежние материалы как историческую версию в документации только при необходимости; не создавать дублирующих «источников истины».

## Ограничения
- **Только прототипы и документация**: без изменений frontend приложения, API, DB, Alembic, бизнес-логики ERP и PC-03. Никаких commit/push/merge.
- Не изменять UI-A–UI-F и ранее утверждённые решения. UI-G/H оставить `READY FOR OWNER REVIEW`, без `OWNER-APPROVED` и общего `DESIGN-APPROVED`.
- Не закрывать `PC-02.1` и `P1 refresh-model` автоматически. Нормы и численность брать только из согласованного capacity contract; неизвестные данные не выдумывать. Дополнительные данные для демонстрации явно маркировать как синтетические.
- SL-UI-BASE-v1, PT-02, DS-SHELL-01/02, single-file HTML со встроенными CSS+JS, адаптивность desktop/tablet/mobile, удобная клавиатурная навигация.

## Проверки / критерии готовности
- Два автономных HTML открываются локально, работают поиск/период/фильтры/drill-down/reset, ссылки между UI-A–UI-H не сломаны.
- Сценарий 100 заказов управляется без бесконечной прокрутки; видна загрузка каждого участка и каждого типа ресурса, одна причина может охватывать много заказов.
- Сценарии нулевой мощности, выходного, ремонта, неизвестной нормы, перегрузки, пересечений, частичных партий, нарушения зависимости и срока представлены без ложного «успеха».
- Проверить Edge на 1440, 1280, 768, 390, 320 px, keyboard, отсутствие горизонтального переполнения; если браузер недоступен — честно зафиксировать непроверенное, не выдавать старые screenshots за новые.
- JS syntax, локальные ссылки, `git diff --check`, roadmap/twin check и доступный project check. Известные baseline 7/10 и P1 держать отдельно; не расширять scope ради них.
- Итог Codex: изменённые файлы, что сделано, какие сценарии проверены, явные открытые вопросы и статус экранов. Остановиться до утверждения владельцем.
