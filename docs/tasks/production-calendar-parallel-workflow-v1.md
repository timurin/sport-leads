# Production Calendar Parallel Workflow v1

## Назначение
Этот протокол действует **только** для модуля:

**Production Calendar / «Очередь производства»**

Он не является общим правилом разработки всего проекта Sport-Leads.

Для любых других модулей Sport-Leads распределение задач между Codex и Cursor определяется отдельно по ситуации.

## Роли в модуле Production Calendar

### Codex
Отвечает за:
- backend;
- PostgreSQL;
- Alembic migrations;
- API;
- service layer;
- data contracts;
- архитектурные и системные изменения;
- backend и integration tests;
- project-wide technical checks, если они относятся к календарю.

### Cursor
Отвечает за:
- frontend;
- UI;
- routes/pages;
- компоненты;
- frontend state;
- frontend tests;
- TypeScript/lint/build;
- локальные UX-исправления календаря.

## Правило параллельной работы
Параллельная работа двух агентов используется только тогда, когда задачи можно разделить на независимые scope без пересечения файлов.

Перед запуском:
1. Зафиксировать backend/frontend contract.
2. Определить зону Codex.
3. Определить зону Cursor.
4. Запретить каждому агенту менять область другого.
5. Интеграцию выполнять отдельной короткой задачей после завершения обеих частей.

## Когда не использовать двух агентов
Не использовать параллельную схему, если:
- оба агента должны менять одни и те же файлы;
- задача слишком мала;
- контракт ещё не определён;
- требуется сначала архитектурное решение;
- параллельность создаёт больше риска, чем пользы.

В таких случаях задача выполняется одним агентом.

## Owner review
Не останавливать разработку после каждой технической микрозадачи.

Проверка владельца требуется только если:
- меняется утверждённый UX/дизайн;
- меняется основной рабочий процесс диспетчера;
- возникает спорная бизнес-логика;
- нужна новая архитектурная развилка;
- требуется рискованная или необратимая migration;
- автоматические проверки не позволяют подтвердить корректность;
- крупный этап календаря готов к итоговой приёмке.

## Общие ограничения
- не делать commit / push / merge без отдельного разрешения владельца;
- не расширять scope «на будущее»;
- не строить MES/APS-функциональность без отдельного решения;
- сохранять принцип лёгкого календаря:
  **минимум ручного ввода, максимум расчёта и подсказок из существующих данных**;
- не исправлять unrelated проблемы проекта, если они не блокируют текущую задачу;
- при конфликте файлов между агентами остановить параллельную работу и переразделить scope.

## Контрольные проверки
По завершении значимой итерации календаря:
- targeted tests;
- full backend tests, если затронут backend;
- full frontend tests, если затронут frontend;
- lint;
- TypeScript;
- production build;
- Alembic checks, если менялись migrations;
- project check;
- git diff --check.

## Приоритет
Для Production Calendar:

**простая рабочая очередь производства > сложная автоматизация планирования**

Любая новая функция должна сокращать время ведения календаря, а не добавлять его обслуживание.
