# Stage 18.3.8 - Technical card print form A4 x2

## Scope

Next unfinished roadmap item after `18.3.7`.

Ship the technical-card consumer slice for the Stage `18.3` print-form registry:

- bind print generation to `binding_type=model`, `binding_key=technical_card`;
- prepare the payload only from existing Stage `9.*` technical-card fields;
- expose Side 1 / Side 2 data blocks required by the approved Excel print layout;
- keep the print entry point on `/production/tech-cards/[id]` without shell changes.

## Constraints

- No parallel technical-card print store or backend domain copy.
- No demo fallback when the active print form is missing.
- Print payload may include pre-rendered HTML fragments for the current registry engine, but raw Stage 9 fields remain in the payload too.
- DS-SHELL-01 / DS-SHELL-02 visual contracts must remain preserved.

## Planned slices

1. Frontend payload builder for `technical_card` print.
2. Server action for registry `POST /print-forms/generate`.
3. Document-header print button wiring on `/production/tech-cards/[id]`.
4. Focused regression for payload and Side 1 / Side 2 fragments.
5. Visual verification on the technical-card document after a live active print form is available.

## Visual checklist

1. `/production/tech-cards/[id]` header action `Печать` opens/generated registry output instead of the old stub.
2. Side 1 (A4 landscape): order info block 100%; mockup 30% + piece-by-piece matrix 70%.
3. Side 2: nomenclature/model with optional model cover photo; separate block «Схема сборки изделия»; materials; operations/volumes.
4. Header action `PDF` downloads registry PDF (`output_format=pdf`).
5. If no active print form is configured for `technical_card`, the document shows an explicit API error.
