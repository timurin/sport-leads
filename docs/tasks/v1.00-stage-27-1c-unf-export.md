## Queue

Owner-pull backlog for **outbound** packages from Sport-Lead to 1C:UNF. **Do not auto-start** `27.1+` except when the owner names a code. Current v1.00 slice is Stage **12.5** (`12.5.1`). Do not interrupt `12.5`.

- Stage `16.1` (website / email / VK / Telegram / telephony)
- Catalog Excel `4.5` (contour A)
- Print-forms `18.3`
- Universal job shell `16.3` as the SoT of 1C documents

## Contract (`27.0.1`, closed `2026-08-26`)

1. Managers run the order on the platform. 1C receives **packages** so УНФ can create its documents.
2. Catalog matching happens **in 1C** (propose similar/equal → link existing or create). No pre-filled УНФ keys (`external_code` / GUID) on the platform. The A=B register lives in УНФ; later loads should show fewer unmatched catalog rows.
3. Every load is **semi-manual** (operator confirms). Documents and catalogs are separate confirmation steps when the УНФ processing exists (out of this repo).
4. Field maps and file volume are **not** written in the roadmap in advance. Describe fields at `27.2.1` / `27.3.1` / `27.4.2` when that export is implemented.
5. Payload must carry **stable platform ids** (order, client, organization, nomenclature, variant, Spec version, export/document id) so УНФ can remember A and stay idempotent.
6. УНФ matching UI / processing is **out of repository**. Sport-Lead only produces the file/package.

## Document pairs (UNF receiver, not entity identity)

Specification on the platform is a plan+fact **report** (ADR-004 / ADR-031), not a shop-floor launch order. УНФ «Заказ на производство» is the **receiver**.

УПД / ТН is **not** a domain document yet (ADR-005 left it out of invoice MVP). `27.4.1` decides: new order child **or** assemble from order + `shipped` / `fg_issue`.
